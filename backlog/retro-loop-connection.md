# レトロ観測サブエージェントの接続点を task-pipeline SKILL.md に定義する

依存: metrics-collect-scan-mode, metrics-fail-reasons

## 背景 / 現状

行番号は commit 33ade02 時点。ずれていたら引用文言で grep すること。

メトリクス (elapsed / executor / verifier / overhead 時間、重複排除済み処理トークン、diff 規模、リトライ回数、fail_reasons) が `~/.claude/task-pipeline/metrics.jsonl` に自動蓄積されるようになっても (依存 2 件の成果)、それを**改善アクションに変換する仕組みが無い**。2026-08-03〜04 の 8 タスク実行では、verifier 時間が elapsed の約 40%、doc 系タスク (変更 16 行に 780 万トークン) への gate:light 適用漏れ、リトライ 4/8 が research/plan の事実精度起因、という改善余地が数字に出ていたが、これらは人が手で集計して初めて見えた。

task-pipeline には枯渇時フロー (SKILL.md「枯渇時フロー」節 — 候補が尽きたとき read-only の調査サブエージェントで内訳を作る) という「一区切りの総括」の既存パターンがあり、レトロはこれと同型の read-only サブエージェント 1 体として接続できる。サブエージェント指示を references/ 配下の別ファイルに置いてパスで渡す形式は `references/pr-watcher.md` 等で確立している。

`docs/metrics/` はまだ存在しない (実測: リポジトリ直下に `docs/` は有るが `docs/metrics/` は無い)。

**出口の設計判断 (2026-08-04 ユーザー決定済み)**: レトロの出口は**報告 + ファイル保存のみ**。トラッカー (backlog/) への自動書き込みはしない。改善候補を issue にするのは人が `/task-prep` に流す操作であり、ready 付与という人間ゲート (approve=auto の安全性の根拠) を現行のまま保つ。

## 要求

1. `task-pipeline/SKILL.md` に「レトロ観測」の節を追加し、次の **3 トリガーのいずれか**で read-only レトロサブエージェント (general-purpose、同期) を 1 体起動する手順を定義する:
   - 枯渇時フロー (最終報告を書く回 — `stalled` が null から `depleted` に変わる最初の 1 回)
   - ループを止めるとき (枯渇・停滞打ち切り・アダプタ不通のいずれの停止経路でも)
   - done 回収 10 件ごと
   「10 件ごと」の基準点 (前回レトロがどこまで見たか) は機械判定できる形で持つこと。持ち方は research/plan で確定してよい (例: 最新サマリーファイルに「集計済み件数」を記録し、metrics.jsonl の現在行数との差で判定する等)。state.json スキーマの変更を伴う場合は `state.ts` の contract との整合も要求に含まれる。
2. レトロサブエージェントの指示は `task-pipeline/references/` 配下の新規ファイルに置き、SKILL.md からはパスで渡す (既存のコンテキスト規律: 指示本文をプロンプトに書き写さない)。指示の内容: `metrics.jsonl` の未総括分 (前回基準点以降) + `fail_reasons` を読み、(a) サマリーを `<プロジェクトルート>/docs/metrics/<UTC日付 YYYY-MM-DD>.md` に書く、(b) 改善候補を構造化 JSON (候補ごとに: 観測された数字の根拠 / 提案 1 行 / 期待される効果) で返す。
3. サマリー md の最低限の書式を定義する: 対象期間・件数、タスク別の elapsed / トークン / リトライの表、fail_reasons の要約、改善候補の一覧。git 管理下に置くのは推移を diff で追えるようにするため。
4. **書き込み先の制限を明記する**: レトロが書いてよいのは docs/metrics/ 配下のサマリーだけ。トラッカー (backlog/ のアイテムファイル・リストファイル) への書き込みはしない。オーケストレーターは返った改善候補を報告に載せ、`/task-prep` への接続コマンド 1 行を添える (人がそれを流すかは人の判断)。
5. レトロの失敗はパイプラインを止めない (収集と同じベストエフォート扱い。history に 1 行残して続行)。

## 受け入れ条件

1. `grep -n "レトロ" task-pipeline/SKILL.md` にヒットがあり、その節に 3 トリガー (枯渇時・ループ停止時・done 10 件ごと) がすべて記載されている。
2. 「10 件ごと」の判定方法が、SKILL.md または references/ の記述だけから第三者が機械的に再現できる (何と何を比べるかが具体的に書いてある)。
3. レトロサブエージェント指示の新規ファイルが `task-pipeline/references/` 配下に存在し、SKILL.md の起動プロンプトがそのパスを渡す形になっている。
4. 指示ファイルに、書き込み先が `docs/metrics/` 配下のサマリー 1 本に限られること、トラッカーへ書き込まないことが明記されている。
5. サマリー md の書式定義 (節構成) が指示ファイルにあり、上記 3 の要素 (期間・件数、タスク別表、fail_reasons 要約、改善候補) を含む。
6. SKILL.md のレトロ節に、失敗時はパイプラインを止めず history に残して続行する旨の明記がある。
7. `sh tests/run.sh` が全スイート PASS (failed: 0。この issue は文書中心のため新規テストは要求しないが、既存テストを壊さないこと)。

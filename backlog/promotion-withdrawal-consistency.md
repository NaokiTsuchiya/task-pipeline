1. **markdown トラッカーで依存昇格が規定上実行できない。** 「マージで解けた依存の昇格」(440 行) は昇格サブエージェントを「read-only + ラベル操作だけ」と規定するが、委任先 task-prep/references/trackers/markdown.md の昇格スキャン (25 行) はバックログのリストファイルへの行追加 = ファイル書き込みであり、制約が禁じる操作である。SKILL.md 231 行自身が markdown の mark を「git 管理ファイルの構造保存編集」としてラベル操作と質的に区別している。さらに委任プロンプトの規定は task-prep の 2 ファイルのパスを渡すだけで、source (リストファイルのパス / owner/repo) を渡す規定が無い — アダプタ呼び出しの定型 (220 行) が `source:` を明示するのと対照的。gh はアダプタ既定 (カレントリポジトリの origin 解決) で通常は救われるが、markdown には source の既定が無く対象を特定できない。source に別リポジトリを明示した gh 運用でも誤対象のリスクが残る。
2. **watcher `merged` 経路の done 処理が限定列挙で誤読余地がある。** 387 行「下記「マージの回収」の done 処理 (mark done、state 更新、worktree 片付け) を行う」の括弧は 3 項目の限定列挙で、同節配下の依存昇格 (436-443 行) と origin 同期 (445-457 行) に触れない。423 行「どちらの経路でも done の処理は同じ」により両後処理が走る読みは成立する (= 完全な欠落ではない) が、枯渇時フロー 466 行が「そこに含まれる依存の昇格まで済ませる」と明示参照するのと非対称で、括弧の 3 項目だけを実行して節の後処理へ進まない読み方を許す。finish=pr のリモートマージ直後は watcher 経路が主経路なので、誤読の実害が最も出やすい。

# PR を押し直したときにも通知を送る (pr_fix / rebase_fix からの復帰)

## 背景 / 現状

行番号は commit 0498660 時点。ずれていたら引用文言で grep すること。

`finish=pr` の通知は現状、**PR ができた最初の 1 回しか送られない**。`task-pipeline/SKILL.md:223` が明示的に禁止している:

> 送るのは **PR / コミットができた最初の 1 回だけ**。`pr_fix` からの復帰 (下の行) では送らない — 指摘に対応して押し直したことは watch 側の追従で見えており、往復のたびに鳴らすと通知の価値が落ちる。

`rebase_fix` 側も同様に `task-pipeline/SKILL.md:226` で明記されている:

> **rebase_fix からの復帰でここに来たときも `mark` を呼び直さず、通知も送らない。**

この設計の前提は「押し直したことは watch 側の追従で見える」だが、**watch が見ているのはパイプライン自身であって人ではない**。レビュアーから見ると、指摘に対応して PR が更新されたことを知る手段が無く、再レビューの契機が失われる。無人運転では「パイプラインが人を待ち始める地点」を通知で埋める設計になっている (`task-pipeline/SKILL.md:219` が最初の 1 回についてそう述べている) のに、2 回目以降の待ちが埋まっていない。

なお最初の 1 回の通知には PR URL が既に入っており、これは仕様どおり機能している (`task-pipeline/SKILL.md:221` のテンプレート `<id> レビュー待ち: <PR URL> — <タイトルを 40 字程度で>`。実測: 全 transcript から抽出した RayDiContext の `finish=pr` 運用 16 本すべてが URL 付きだった。例 `gh-113 レビュー待ち: https://github.com/NaokiTsuchiya/RayDiContext/pull/123 — AppMeta の相対パス compileDir/tmpDir 受理バグを修正`)。**本 issue が足すのは更新時の通知であって、最初の 1 回の文面は変えない。**

### PR が更新される経路は 3 つある

| 経路 | 場所 | 現状 | 本 issue の扱い |
|---|---|---|---|
| (a) `pr_fix` 復帰 | `task-pipeline/SKILL.md:227` | 送らない (:223 が禁止) | **送る** |
| (b) `rebase_fix` 復帰 | `task-pipeline/SKILL.md:226` | 「通知も送らない」 | **送る** |
| (c) 素の載せ直しの force push | `task-pipeline/SKILL.md:386` (「残った PR を新しい基点へ載せ直す」手順 4) | 通知なし・報告のみ | **送らないまま** |

(c) を除外するのは、diff の意図が変わらない (基点が動くだけ) うえに、**マージのたびに open PR の本数だけ鳴る**ため。レビュアーが見直すべき内容は変わっていない。(a) と (b) はどちらも内容が変わり、かつ検証ゲートを通っている点で共通する。

通知の本数は青天井にならない。`pr_fix` は `watch.fix_attempts` の上限 3 で頭打ちになる (`task-pipeline/SKILL.md:320`「**3 を超えたら修正しない**」)。

## 要求

1. `task-pipeline/SKILL.md:223` の「`pr_fix` からの復帰 (下の行) では送らない」という禁止を取り除き、**送る**規則に置き換える。禁止の根拠として書かれている理由 (「watch 側の追従で見えており」) も、実態に合わないので残さない。
2. `task-pipeline/SKILL.md:226` の `rebase_fix` 復帰から「通知も送らない」を取り除き、同じく送る規則にする。
3. 更新時の通知の文面要件を定める。**最初の 1 回の通知 (`:221` のテンプレート) は変更しない。** 更新時の文面は既存の制約をすべて引き継いだうえで、次を満たすこと:
   - `PushNotification` / `status: "proactive"` / 200 字未満・1 行・markdown 無し
   - **新規作成ではなく更新だと判別できる語**を先頭付近に置く (レビュアーが「もう見た PR か」を一目で判断できるようにするため)
   - **PR URL を含める**
   - 何が変わったかを 1 語句で添える — `pr_fix` なら対応した指摘の件数、`rebase_fix` なら衝突解消と載せ直し先
   - **CI の状態や検証の結果は書かない** (`:225` の既存制約をそのまま引き継ぐ。押し直した直後は CI が回り始めてすらいない)
4. 送る位置は**レビュー待ち処理が成功した後**とする。`pr_fix` 経路は `fix-done` → `in-review` の順序制約 (`task-pipeline/SKILL.md:227`) があるので、その後に送る。状態の書き込みが失敗した場合に通知だけ出ることがないようにする。
5. `PushNotification` が使えない環境では何もしない (`:224` の既存規定をそのまま引き継ぐ。送れないことを失敗として扱わず、フェーズも止めない)。
6. (c) 素の載せ直しでは送らないことと、その理由を SKILL.md に明記する (将来「なぜここだけ送らないのか」を再検討させないため)。

## 受け入れ条件

1. `grep -n "pr_fix. からの復帰 (下の行) では送らない" task-pipeline/SKILL.md` がヒットしない。
2. `grep -n "通知も送らない" task-pipeline/SKILL.md` がヒットしない。
3. `pr_fix` 復帰の記述に通知を送る手順があり、その文面定義に PR URL が含まれることが読み取れる。
4. `rebase_fix` 復帰の記述に通知を送る手順があり、その文面定義に PR URL が含まれることが読み取れる。
5. 更新時の通知が新規作成時の通知と文面上区別できることが SKILL.md に明記されている (「更新だと判別できる語を置く」という要件そのものが記述されている)。
6. 最初の 1 回の通知テンプレート (`<id> レビュー待ち: <PR URL> — <タイトルを 40 字程度で>`) が変更されていないことを `git diff` で確認できる。
7. 更新時の通知にも「CI の状態や検証の結果は書かない」制約が及ぶことが明記されている。
8. 通知を送るのが状態の書き込み (`fix-done` / `in-review` / `rebase-done`) の成功後であることが、手順の順序として読み取れる。
9. 「残った PR を新しい基点へ載せ直す」節 (現行 :386 付近) に、素の force push では通知を送らないことと理由が明記されている。
10. `git diff --stat` の変更が `task-pipeline/SKILL.md` のみで、他ファイルに波及していない。
11. `sh tests/run.sh` が全スイート PASS (failed: 0)。

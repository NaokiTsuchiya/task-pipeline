# 検証の required_fixes を一括で挙げさせ、逐次発見でリトライ上限を使い切らないようにする

## 背景 / 現状

`task-pipeline/SKILL.md` の「リトライ上限」(349 行) は 1 フェーズにつき検証を最大 3 回 (初回 + リトライ 2 回) とし、3 回目も FAIL ならタスクを blocked にする。一方 `task-pipeline/references/verifier.md` には、**検出した不足を 1 回の判定にまとめて出すことを求める記述が無い** (「一括」「まとめて挙げ」「次回に回さ」のいずれも 0 件、2026-08-02 に grep で確認)。

この 2 つが組み合わさると、検証エージェントが毎回 1〜2 件ずつ不足クラスを出すだけで、成果物の質に関係なく上限に達する。

**実際に起きた** (`readme-list-sync`、2026-08-02):

| 回 | 指摘された不足クラス |
|---|---|
| 0 | 表の無い節への挿入 / 節外の表を壊す実装 / 「POSIX sh 依存ゼロ」の検証可能条件 |
| 1 | `。` と `. ` が共存する description の優先規則 / `-h`\|`--help` |
| 2 | `'` 囲みの description / 一覧節が EOF で終わる README |

各回の指摘は `verifier.md` の基準に照らしていずれも正当で、実行エージェントは毎回すべて修正している。それでも 3 回で尽きた。判定は `.task-pipeline/runs/readme-list-sync/verdicts/plan-0.json` / `plan-1.json` / `plan-2.json` に残っている。

なお同タスクには「仕様の枝が多すぎる」という別の原因もあり、そちらは本文の非目標を閉じることで対処済み (`backlog/readme-list-sync.md`)。本 issue は**上限を使い切らせる側の構造**だけを扱う。

## 要求

1. `task-pipeline/references/verifier.md` に、**FAIL を返すときは当該フェーズで検出した不足を `required_fixes` に一括で挙げ、次回の判定に持ち越さない**ことを明記する。「テスト網羅の最低ライン」で不足クラスを挙げるときは、成果物が宣言した分岐を**最後まで走査してから**返す、という形で書く。
2. 同時に、**一括にできない場合の扱い**も書く: 前段の指摘を直した結果はじめて見えるようになる不足 (例: 実装が変わってはじめて到達する経路) は持ち越しになりうる。その場合は判定 JSON にその旨を 1 行残す — 「なぜ前回出せなかったか」が読めれば、上限に達したときに人が原因を切り分けられる。
3. `task-pipeline/SKILL.md` のリトライ上限 (349 行) の側は**変えない**。回数を増やすのは「毎回新しい不足が出る」構造への対処にならないので、本 issue の範囲外とする。

## 受け入れ条件

1. `grep -c '一括' task-pipeline/references/verifier.md` が 1 以上で、その記述が `required_fixes` を対象にしており、「次回に回さない」旨を含む。
2. 「テスト網羅の最低ライン」節に、不足クラスを挙げる前に成果物の宣言した分岐を最後まで走査する旨が書かれている。
3. 持ち越しが避けられない場合に判定 JSON へ理由を 1 行残す規定がある。
4. `task-pipeline/SKILL.md` の 349 行 (リトライ上限) に差分が無い (`git diff -- task-pipeline/SKILL.md` に該当行が現れない)。
5. `verifier.md` の既存の判定基準 (PASS/FAIL の条件、フェーズ別の見どころ、宣言の再判定) を弱めていない — 追加のみで、既存の要求文の削除が無いことを diff で確認できる。

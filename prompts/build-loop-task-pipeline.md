# Fable への依頼プロンプト: `/loop` タスク実行パイプライン skill の構築

---

## 背景と目的

私は個人の skill 群を管理するリポジトリ (`NaokiTsuchiya/skills`) を作り始めたところで、いまはまだ空です。最初に置きたいのが、**自分の issue トラッカーに溜まったタスクを、承認したものだけ自動で片付けていくパイプライン** です。

これが動くと私にとって何が変わるかというと、朝に「今日やっていいタスク」を選んで承認しておけば、あとは Claude Code が `/loop` で回りながら 1 タスクずつ、フェーズを踏んで実装し、フェーズごとに検証を通し、詰まったところだけ私に上げてくる、という状態になります。つまり **承認と、本当に人間しか答えられない判断だけが私の仕事になる** のがゴールです。逆に言えば、私が見ていない時間に勝手に止まったり、検証していない仕事を「終わりました」と報告してきたりすると、この仕組みは価値がゼロになります。そこが一番重要な品質基準です。

あなたには、この skill をリポジトリの最初のコンテンツとして、設計から実装、動作確認まで一気通貫でやってほしい。

## 作ってほしいもの

Claude Code の skill として `/loop` から繰り返し起動される、以下の 3 段構成のパイプライン。

### 1. タスク取得 (トラッカーアダプタ)

指定された issue トラッカーから「実行タスクリスト」を読み出します。トラッカーは**アダプタ層で抽象化**し、起動時の引数か設定で切り替えられること。

- **今回実装するのは、リポジトリ内の markdown task list のアダプタだけ** です。これを最初の実装かつリファレンス実装とします。
- 将来 **Jira / GitHub Issues / Notion** を追加します。MCP が使えるトラッカーは MCP 経由で読むのが前提です。今回は実装しませんが、**その 3 つを後から足すときにアダプタ 1 枚の追加で済む** 形になっているかどうかが、この層の設計の合否基準です。ただし、まだ存在しないトラッカーのために抽象化を過剰に作り込まないでください。3 つを実際に足す手順が短く書けるなら、その抽象度で十分です。

### 2. 承認 (ユーザー確認)

読み出したタスクのうち実行すべきものを私に提示し、承認を取ります。

- `/loop` は私が見ていない時間にも回ります。**毎イテレーションで私に聞くのは設計として失敗** です。承認は先にまとめて取り、承認済みタスクの集合を永続化して、以降のイテレーションはそこから黙って消化していく形にしてください。
- 承認済みタスクが尽きたときの振る舞い (次の候補を提示して待つのか、静かに終わるのか) は、`/loop` の実際の挙動を確認したうえであなたが決めて、理由とともに教えてください。

### 3. 実行 (固定フェーズパイプライン)

承認済みタスクを 1 つずつ、**固定のフェーズパイプライン** に通します。

役割分担の原則はこうです。`/loop` のメインコンテキストは **判断だけを持ち、状態はディスクに置いて毎回読み直す**。承認済みタスクの集合のような状態をコンテキストに抱えると、周回するほど太っていきます。同様に、トラッカーの生の一覧をメインコンテキストに読み込むのも避けてください (MCP 経由なら tool スキーマの分も乗ります)。アダプタ側のサブエージェントに読ませて、小さな構造化結果だけ返させる方が筋が良いはずです。承認のやり取りだけは、私がそこにいる以上メインコンテキストでやるしかありません。

そのうえで、承認済みタスク 1 件につき **長命な実行サブエージェントを 1 体** 立て、そのサブエージェントが全フェーズを同じコンテキストのまま通してください。フェーズごとに実行者を切り替えないこと。フェーズ間で引き継ぐ文脈をプロンプトに書き起こす作業が発生し、そこが劣化点になります。

メインコンテキストに 1 イテレーションあたり何が積まれるかが、この設計の効き所です。上の配分は私がドキュメントから推測して書いたものなので、`/loop` がイテレーション間で実際に何を引き継ぐのかを確認したうえで、あなたの判断で変えてください。変えるなら理由を教えてください。

検証サブエージェントだけは別で、**フェーズごとにフレッシュなコンテキスト** で立ててください。ここでサブエージェントを分ける理由は独立性であり、実行サブエージェントの思い込みを引き継がないことに価値があります。

さらに細かい並列化 (たとえば調査フェーズ内の独立した調べ物) は、実行サブエージェントの中で必要に応じてファンアウトさせてください。ただし本当に独立なものだけにしてください。

- フェーズ構成は skill 側に持たせた固定のものにします (調査 → 計画 → 実装 → 検証 → 報告、あたりを想定していますが、この粒度が妥当かはあなたの判断で決めてください。変えるなら理由を教えてください)。
- **各フェーズは必ずアウトプット (成果物) を出し、そのアウトプットが検証を通ってから次のフェーズに進む** こと。検証を通らなかったフェーズをそのまま次に進めることは、どんな理由があっても許容しません。
- 検証は **フレッシュコンテキストの検証用サブエージェント** が、そのフェーズの仕様に対して行います。実行エージェント自身による self-critique では代替しないでください。検証サブエージェントが不合格を出したときのリトライ回数と、リトライを使い切ったときの扱いはあなたが決めてください。

## 制約

- 承認済みタスクの実行は、**私が見ていない前提** で進めてください。可逆で、かつ元の依頼から素直に follow する操作は、聞かずにやってください。止まっていいのは、破壊的・不可逆な操作、本当のスコープ変更、私にしか出せない入力が要るときだけです。止まるなら質問してターンを終えてください。「このあと〜します」という約束でターンを終えないこと。
- 進捗を報告する前に、各主張をこのセッションの実際のツール結果に照らして確認してください。証拠を指させる仕事だけを報告し、未検証のものは未検証と明言してください。テストが落ちたなら出力とともにそう言い、飛ばした手順は飛ばしたと言い、終わって検証できたものは曖昧にせず終わったと言ってください。
- 依頼の範囲を超えた機能追加・リファクタリング・抽象化はしないでください。起こり得ないケースのためのエラーハンドリングやフォールバックも不要です。いま一番シンプルに、よく動くものを作ってください。
- リポジトリは空です。skill 以外のディレクトリ構成やドキュメントは、この skill を成立させるのに必要な分だけ作ってください。
- 私への応答は日本語でお願いします。

## 生成物 (skill) 自体に必ず入れてほしい指示

この skill は Claude Code に自律実行させるものなので、skill の指示文には最低限、以下の趣旨を含めてください。文言は下記をそのまま使っても、必要に応じて調整しても構いません。

```text
You are operating autonomously. The user is not watching in real time and cannot answer questions mid-task, so asking "Want me to…?" or "Shall I…?" will block the work. For reversible actions that follow from the original request, proceed without asking. Before ending your turn, check your last paragraph. If it is a plan, an analysis, a question, a list of next steps, or a promise about work you have not done ("I'll…", "let me know when…"), do that work now with tool calls. End your turn only when the task is complete or you are blocked on input only the user can provide.
```

```text
Before reporting progress, audit each claim against a tool result from this session. Only report work you can point to evidence for; if something is not yet verified, say so explicitly. Report outcomes faithfully: if tests fail, say so with the output; if a step was skipped, say that; when something is done and verified, state it plainly without hedging.
```

```text
Pause for the user only when the work genuinely requires them: a destructive or irreversible action, a real scope change, or input that only they can provide. If you hit one of these, ask and end the turn, rather than ending on a promise.
```

一方で、**skill を書きすぎないでください**。細かい手順を全部列挙した指示書は、それを読む Claude の質をむしろ下げます。ゴールと境界と検証条件を書き、判断は読み手のモデルに委ねる粒度にしてください。

## 進め方

1. まず、この依頼をスコープしてください。`/loop` skill が実際にどう起動され、イテレーション間で何が引き継がれるのかを **推測ではなく確認** してから設計に入ってください (`/loop` の実装や Claude Code の skill 仕様が手元で読めるはずです)。
2. 設計上、私に決めてほしいことがあれば、この時点でまとめて聞いてください。後出しの質問より、いま聞かれる方がありがたいです。
3. 独立した調査 (トラッカーアダプタの調査、`/loop` の仕様確認、skill の書式調査など) はサブエージェントに投げて、あなたは並行して作業を進めてください。サブエージェントが脱線したり文脈不足になっていたら介入してください。
4. 作りながら自分の仕事をチェックする方法を確立し、**節目ごとにサブエージェントを使って仕様に対する検証を回してください**。あなたが作っているのが「フェーズごとに検証するパイプライン」である以上、その作り方自体が検証されていないのは筋が通りません。
5. 完成したら、markdown task list アダプタで **実際に end-to-end で動かして** ください。ダミーのタスクリストを用意して、承認から実行、フェーズ検証、報告まで一周させ、観測した挙動を報告してください。テストが通ったこと、型が通ったことは、動いたことの証拠にはなりません。
6. コミットや push は、私が明示的に頼むまでしないでください。

## 完成の判定基準

- markdown task list から承認 → 実行 → フェーズ検証 → 報告までが、実際に一周した記録がある。
- 検証サブエージェントが不合格を返したときに、パイプラインが次フェーズへ進まないことが実際に確認できている (意図的に落として確かめてください)。
- Jira / GitHub Issues / Notion の各アダプタを後から足す手順が、短く書き下せる。
- 私が見ていない時間に回して、勝手に止まらず、やっていない仕事を報告しない。

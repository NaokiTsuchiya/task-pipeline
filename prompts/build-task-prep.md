# Fable への依頼プロンプト: task-pipeline に渡す issue を用意する skill の構築

> 2026-07-26 時点の依頼文の記録。現行仕様は task-pipeline/SKILL.md・task-prep/SKILL.md を見よ。

## 背景と目的

私は個人の skill 群を管理するリポジトリ (`NaokiTsuchiya/skills`) を持っていて、そこには今 `task-pipeline` という skill が入っています。issue トラッカー (アダプタで抽象化、GitHub Issues とローカル markdown が実装済み) から承認済みタスクを読み、`/loop` の各イテレーションで 1 件ずつ、research → plan → implement → report の固定フェーズで自動実行するものです。各フェーズはフレッシュな検証サブエージェントの PASS なしに先へ進みません。

まず現物を読んでください。以降の依頼はこれを前提にしています。

- `task-pipeline/SKILL.md` — オーケストレーターの本体
- `task-pipeline/references/executor.md` / `verifier.md` — 実行と検証
- `task-pipeline/references/adapter-protocol.md` と `references/adapters/` — トラッカー抽象化
- `README.md` — 使い方と設計メモ

この仕組みのゴールは、**私の仕事を「承認」と「人間にしか答えられない判断」だけにする**ことでした。ところが実際にはその手前に、まだ私の仕事が丸ごと残っています。**issue を書く**という仕事です。

しかもこれは、あとから足せる周辺作業ではなく、パイプラインの成否をほぼ決める部分です。理由は verifier の作りにあります。report フェーズの検証ゲートは、計画を経由せず **タスク本文の要求を最終状態に直接照合** します。つまり issue 本文に検証可能な受け入れ条件が書かれていなければ、そもそも PASS の出しようがありません。曖昧な issue は検証 3 回 FAIL で blocked に落ちるか、もっと悪ければ「それらしい何か」が実装されて in_review に来ます。逆に、要求と受け入れ条件がはっきりしていて、粒度が 1 サイクルに収まっていれば、パイプラインは私が見ていない間に淡々と回るはずです。

そこで、**私が頭の中で持っている「やりたいこと」を投げると、調査済み・分解済み・依存関係整理済み・受け入れ条件付きの issue 群になって、あとは承認するだけで task-pipeline が回る状態になる**、という skill を作ってほしい。これができると、私の作業は「やりたいことを口に出す」「人間にしか答えられない問いに答える」「承認する」「レビューする」の 4 つだけになります。

## 作ってほしいもの

Claude Code の skill として、大きく次の 2 つの能力。

### 1. 分解 — ぼんやりした要望を、実行可能な issue 群にする

入力は「認証まわりを直したい」「この機能を足したい」程度の、粒度も範囲も定まっていない要望、あるいは既に立っている大きすぎる issue です。

- **推測ではなく実際のコードベースを調査した上で** 分解してください。影響範囲、既存の実装、既に似たものがあるか、といったことを調べずに切った分解は、この skill の価値の大半を失います。
- 分解の粒度基準は「task-pipeline の executor 1 体が research → plan → implement → report を 1 回通せるサイズ」です。具体的な線引きはあなたが決めてください。判定材料は `executor.md` と `verifier.md` にあります。
- **依存関係を整理してください。** ここは特に注意が要ります。task-pipeline は依存関係という概念を持っていません。承認された順 (gh なら issue 番号の昇順) に 1 件ずつ実行するだけです。したがって「依存が解けていない issue がパイプラインに拾われない」ことを、準備側で保証する必要があります。どう保証するかはあなたが決めてください。
- 既存 issue との重複も見てください。同じことを言っている issue を増やすのは、この skill の逆の仕事です。

### 2. 深掘り — 1 つの issue を、検証可能なところまで精緻にする

入力は既存の issue 1 件です。出力は同じ issue が精緻になった状態。

- 最低限の合否は「**実装が終わったあと、その issue しか読んでいない第三者が、要求を満たしたかどうかを PASS / FAIL で判定できるか**」です。これは verifier がやることそのものなので、基準を verifier に合わせています。何をどう書けばそうなるかは、`verifier.md` を読んだあなたの判断で決めてください。テンプレートを厳密に決めたいわけではありません。
- ここでも調査を伴います。issue に書くファイルパス・関数名・現状の挙動は、実際のコードで裏を取ってから書いてください。**間違った現状認識が書かれた issue は、自動実装をまっすぐ間違った方向へ走らせます。** 裏が取れなかったことは、取れたことと同じ調子で書かないでください。
- **人間にしか答えられない不明点を、勝手に決めて埋めないでください。** ここがこの skill の一番危ないところです。仕様の選択、優先順位、外部との約束、私の好み。これらを推測で埋めた issue は、間違った仕様のまま自動で実装まで到達してしまいます。私に聞く、あるいは未確定として残して準備完了にしない。どちらでもいいですが、勝手に決めるのだけはしないでください。

### 3. この 2 つの組み合わせ

私が実際に使うときの流れは「大きい要望 → 分解 → 出てきた issue をそれぞれ深掘り → 承認して task-pipeline へ」です。1 件だけ手元にあるときは深掘りだけ、深掘りの途中で大きすぎると分かったら分解へ、という行き来もあります。

この 2 つを**どう組み合わせるかも含めて設計してください**。skill 2 枚にするのか、1 枚に 2 つの入口を持たせるのか、私が毎回どちらかを選ぶのか、一方が必要に応じて他方を呼ぶのか。あなたが決めて、理由を一言添えてください。

### 接続の合否基準

準備が終わった状態の issue に対して `/loop /task-pipeline <tracker> <source>` を起動したら、**準備済みのものだけがそのまま候補に上がって回り始める**こと。task-pipeline 側に手を入れないと接続できないなら、それは準備側の設計が間違っているサインです (どうしても必要なら理由とともに最小限の変更は構いません)。

## あなたに決めてほしいこと

以下は私が決めていません。設計に入る前にまとめて聞いてくれるのが一番ありがたいですが、あなたが判断できるものは判断して、理由を一言添えてくれる形でも構いません。

- skill の分け方 (上記)
- **トラッカーへの書き込みをどう扱うか。** task-pipeline には既にアダプタ層があります (`list` / `mark` の 2 操作)。準備側は issue の **作成・本文更新** が要るので、そのままでは足りません。既存アダプタ層を拡張するのか、準備側で独立に持つのか、当面 GitHub Issues 決め打ちにするのか。私が主に使うのは GitHub Issues です。**まだ存在しない使い方のために抽象化を作り込まないでください。**
- 依存関係の表現方法と、依存未解決の issue を task-pipeline に拾わせない仕組み
- 「準備完了」をトラッカー上でどう表すか (task-pipeline の gh アダプタは `?label=ready` のようなラベル絞り込みができます)
- 分解結果を私に承認させるタイミングと粒度

## 制約

- **issue を実際に作る前に、対象リポジトリを私に確認してください。** issue の作成と本文の書き換えは外向きで、消しにくい行為です。動作確認で実 issue を作るなら、どこに作るかは私が決めます。ローカル markdown トラッカーで完結できる部分は、そちらで先に確かめてくれて構いません。
- 依頼の範囲を超えた機能追加・リファクタリング・抽象化はしないでください。起こり得ないケースのためのエラーハンドリングやフォールバックも不要です。いま一番シンプルに、よく動くものを作ってください。
- **skill を書きすぎないでください。** 手順を全部列挙した指示書は、それを読む Claude の質をむしろ下げます。ゴールと境界と合否条件を書いて、判断は読み手のモデルに委ねる粒度にしてください。既存の `task-pipeline/SKILL.md` がその意図で書かれているので、濃さの基準にしてください。もし既存 skill 側に、今のモデルにはもう不要なほど細かい指示を見つけたら、指摘だけしてください (直すかは私が決めます)。
- 情報が揃ったら動いてください。既に決まったことを再検討したり、取らない選択肢を私向けの文章で並べたりは不要です。選択肢を天秤にかけているなら、網羅ではなく推奨を出してください。
- 進捗を報告する前に、各主張をこのセッションの実際のツール結果に照らして確認してください。証拠を指させる仕事だけを報告し、未検証のものは未検証と明言してください。テストが落ちたなら出力とともにそう言い、飛ばした手順は飛ばしたと言い、終わって検証できたものは曖昧にせず終わったと言ってください。
- 私への応答は日本語でお願いします。最後のまとめは、途中の作業を見ていない読み手に向けて書いてください。結論を最初の 1 文に置き、作業中に自分で作った略語や記号の羅列は持ち込まないこと。
- コミットや push は、私が明示的に頼むまでしないでください。

## 進め方

1. まずこの依頼をスコープしてください。`task-pipeline` の現物、`/loop` の挙動、Claude Code の skill 仕様は、**推測ではなく手元で確認**してから設計に入ってください。
2. 決めてほしいことがあれば、この時点でまとめて聞いてください。後出しの質問より、いま聞かれる方がありがたいです。
3. 独立した調査 (既存 skill の読み込み、GitHub の issue 操作手段の確認、依存関係の表現方法の調査など) はサブエージェントに投げて、あなたは並行して作業を進めてください。サブエージェントが脱線したり文脈不足になっていたら介入してください。
4. 作りながら自分の仕事をチェックする方法を確立し、**節目ごとにフレッシュなサブエージェントで仕様に対する検証を回してください**。
5. 完成したら **実際に end-to-end で動かして** ください。テストが通ったこと、ファイルが書けたことは、動いたことの証拠になりません。最低限:
   - わざと曖昧な要望を 1 つ与えて分解させ、出てきた issue を深掘りさせる (要望は私が出します。無ければあなたが決めて構いませんが、その場合はこのリポジトリ自身に対する要望にしてください)
   - そのうち 1 件を実際に task-pipeline に通し、検証 FAIL を繰り返さずレビュー待ちまで到達するかを見る
   - 観測した挙動を報告してください。うまくいかなかった点は、うまくいった点と同じ密度で書いてください。

## 完成の判定基準

- 曖昧な要望 1 つから、実コードの調査に基づいた複数の issue と依存関係が、実際に作られた記録がある。
- そこで作られた issue のうち少なくとも 1 件が、task-pipeline を通ってレビュー待ちまで到達している。検証 FAIL を繰り返さずに通ったかどうかも見たい。
- 依存が解けていない issue が、パイプラインに拾われないことが実際に確認できている (意図的に依存のあるものを作って確かめてください)。
- 人間にしか答えられない不明点が、勝手に埋められずに私のところへ上がってくる (意図的に判断の要る曖昧さを混ぜて確かめてください)。
- `/loop /task-pipeline` 側に手を入れずに (あるいは最小の変更で) 接続できている。

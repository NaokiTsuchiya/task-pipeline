# Fable への依頼プロンプト: リポジトリを見渡して次にやるべきことを出す

以下をそのまま渡す。`<REPO>` は対象リポジトリの絶対パスに置き換える。

---

## 背景

私は `<REPO>` の開発に 2 つの skill を使っています。

- **task-prep** — 要望を、検証可能な受け入れ条件と依存関係を備えた issue 群に変える。書き込む前に必ず私の承認を取る
- **task-pipeline** — `ready` ラベルの付いた issue を 1 件ずつ、research → plan → implement → report の固定フェーズで自動実行し、PR を出してレビューコメントまで追従する。各フェーズはフレッシュな検証サブエージェントの PASS なしに先へ進まない

この 2 つで、私の仕事は「何を作るか決める」「人間にしか答えられない問いに答える」「PR をレビューしてマージする」の 3 つまで削れています。パイプラインは 1 タスクあたり 25〜40 分で PR まで到達するので、**`ready` の在庫はすぐ尽きます**。尽きた時点で止まるのは、次に何をやるかを誰も決めていないからです。

「何を作るか」を自動で決めさせないのは意図的な線引きです。下流には検証ゲート・CI・自動レビュー・私のマージがあるので、間違ったものが黙って入ることは起きません。希少なのは正しさではなく**私のレビュー時間**で、それを何に使うかは私が決めたい。

そこであなたには、**決定の手前まで**をやってほしい。リポジトリを実際に読んで、次に手を入れるべき候補を出し、順位を付けて、私が選べる形にしてください。選ぶのは私です。

## 最初に読むもの

推測で書かないでください。ここで挙げたものは実際に読んでから始めてください。

- `<REPO>` のコード全体 (規模に応じてサブエージェントに分担させてよい)
- `CLAUDE.md` — この repo の規約。テストの走らせ方や禁止事項が書いてある
- `docs/decisions.md` — **特に重要**。「意図的にそうしている、戻すな」と「コストが見合わないので見送った」が記録されています。ここに載っている判断を蒸し返す提案は、それだけで的外れです
- open な issue 全部 — 既に立っているものと重複する提案には価値がありません
- 直近 1〜2 週間のマージ履歴 — 何が動いている最中かを掴むため

## 出してほしいもの

次に着手する価値のある候補を、**多くて 8 件**。数を埋めることが目的ではないので、根拠の弱いものを足すくらいなら 3 件で構いません。

種類は問いません。欠陥やリスクの解消でも、保守性の改善でも、新しい機能でも、開発体験の改善でもよい。ただし**それぞれについて次を書いてください**。

1. **何をするか** — 1〜2 文
2. **なぜ今か** — 何が困っているのか、放置するとどうなるのか。ここが弱い候補は落としてください
3. **裏取り** — 主張の根拠になるファイルパスと行番号、コマンドの実出力。「テストが遅い」ではなく「`composer tests` が 12.4 秒で、うち 8.1 秒が `BinCompileTest` のサブプロセス起動」のように
4. **受け入れ条件の案** — 実装後に、その issue しか読んでいない第三者が PASS / FAIL を判定できる形。コマンドか観測で判定できること。これが書けない候補は、**書けないという事実ごと報告してください** (私の判断が要るという印です)
5. **規模** — task-pipeline の executor 1 体が 1 コンテキストで通せるか。超えるなら分割案も
6. **依存** — 他の候補や既存 issue に依存するか

最後に、**私ならこの順でやる**という順位と理由を付けてください。網羅的な比較表ではなく、推薦を。

## やらないこと

- **トラッカーに書き込まない。** issue を作らない、既存 issue の本文やラベルを変えない、コメントもしない。提案は私に見せるだけです。承認したものは私が task-prep に渡します
- **実装しない。** ブランチを切らない、コミットしない、コードを直さない。調査のために一時ファイルを作るのは構いませんが、リポジトリの作業ツリーは元のままにしてください
- **`docs/decisions.md` で決着している話を蒸し返さない。** 蒸し返す価値があると考えたなら、その判断が書かれた時点から何が変わったのかを先に示してください
- **既存 issue と重なるものを新規候補として出さない。** 重なりに気づいたら、既存 issue の番号を挙げて「これを深掘りすべき」と書いてください

## 進め方

独立した調査はサブエージェントに並列で投げて、待っている間も自分の作業を進めてください。サブエージェントが的を外していたり、必要な文脈を持っていないと分かったら介入してください。

長く走る場合は、自分の作業を検証する方法を決めて、一定の区切りごとにフレッシュなサブエージェントで確かめてください。特に「裏取り」として書いた行番号やコマンド出力は、後から別のエージェントに再実行させると誤りが見つかります。

進捗を報告する前に、主張ひとつひとつをこのセッションの実際のツール結果と突き合わせてください。証拠を指せるものだけを報告し、未確認のものは未確認と明示してください。テストが落ちたなら出力付きでそう言い、飛ばした手順があるならそう言ってください。確認できたことは、ぼかさずそのまま書いてください。

必要な情報が揃ったら動いてください。既に確定している事実を導き直したり、私が決めたことを蒸し返したり、採らない選択肢を並べたりしないでください。迷ったときは網羅的な比較ではなく推薦を出してください。

私が答えなければ進めない場合 — 仕様の選択、優先順位、外部との約束 — だけ、そこで止まって聞いてください。それ以外は進めてください。

## 報告のしかた

この作業は私が見ていない間に進むので、最後のメッセージが私にとっての最初の 1 枚になります。作業を続けた文章ではなく、**知らない人に説明し直す文章**として書いてください。

結論を最初の 1 文に置いてください。「何を見つけたか」「次に何をすべきか」です。そのあとに詳細を。作業中に使った略語や、あなたが途中で作った呼び名は持ち込まないでください。ファイル名・コミット・フラグに触れるときは、それぞれに平易な説明の節を付けてください。矢印の連鎖や記号での省略は使わず、文にしてください。短さと分かりやすさが両立しないときは、分かりやすさを取ってください。

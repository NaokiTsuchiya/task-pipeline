# task-prep — 要望を task-pipeline の入力に変える

あなたは task-pipeline の**上流**である。出力 (issue 本文) の読み手は人間だけではなく、task-pipeline の executor と verifier である。verifier は最後の report フェーズで、計画を経由せず **issue 本文の要求を実装後の最終状態に直接照合する**。この skill の合否は、書いた issue がその照合に耐えるかで決まる。曖昧な issue は検証 FAIL の連発か、もっと悪ければ「それらしい何か」の自動実装に化ける。

ユーザーの仕事を「やりたいことを口に出す」「人間にしか答えられない問いに答える」「承認する」「レビューする」の 4 つに絞ることがゴールである。それ以外 (調査・分解・裏取り・依存整理・文面化) はすべてこちらの仕事。

## 入口

`$ARGUMENTS`: `<tracker> [source] <入力>`。source の意味は task-pipeline と同じ (`gh` は省略でカレントリポジトリ、`markdown` はリストファイルのパス) だが、切り分けは違う — **tracker 直後のトークンが source の形 (markdown: パス、gh: `owner/repo`) のときだけ source として取り、残りはすべて入力**。入力の形で入口を選ぶ:

- **要望テキスト** (「認証まわりを直したい」等) → 分解
- **issue 参照** (`#42` / issue URL / markdown の id) → 深掘り
- **入力なし** → 棚卸し (下記「棚卸し」)

分解と深掘りは一方通行ではない。分解で生まれた各 issue は ready 基準まで深掘りしてから書き込む。深掘りの途中で 1 サイクルに収まらないと分かったら分解に切り替える。既に立っている大きすぎる issue の参照を渡されたら、それは「その issue を分解する」依頼である。

どの入口でも、最初に昇格 (下記「依存」) を済ませてから本題に入る。

## ready 基準 (この skill の合否条件)

issue は次をすべて満たすとき、そのときだけ ready (task-pipeline の候補) にできる:

1. **第三者判定可能**: 実装完了後に、その issue しか読んでいない第三者が、要求を満たしたかを PASS / FAIL で判定できる。要求はすべて、コマンドか観測で判定できる受け入れ条件に覆われている。
2. **裏取り済み**: 本文中のファイルパス・関数名・現状挙動は、実際のコードで確認してから書いてある。確認できなかった記述を、確認できたものと同じ調子で書いていない (未検証と明記するか、削る)。間違った現状認識は自動実装をまっすぐ間違った方向へ走らせる。位置と数値の書き方は下記「位置参照と数値」に従う — **行番号だけで位置を指した記述は、腐ったときに検出できないので裏取り済みとみなさない**。
3. **人間の問いが残っていない**: 本文に `未確定:` 行 (下記) が残っていない。
4. **粒度が 1 サイクル**: 下記「粒度」に収まる。
5. **依存ゼロ**: 依存する issue がすべて Done (マージ/受け入れ済み) である。本文が完成していても、依存が残るなら ready にせず依存待ちとして記録する (表現はトラッカー別: references/trackers/)。

本文の形式は固定しない。ただし、要求と受け入れ条件が区別して読めること、`依存:` と `未確定:` は下記の書式で書くこと (機械的に走査するため)。

## 位置参照と数値

裏取りした事実は、**書いた瞬間から腐り始める**ことを前提に書く。issue が実装されるまでの間に main は進み、指した場所はずれる (実測: 2026-08-05 に skills リポジトリで行番号を書いた 4 issue のうち 3 件が数時間で腐った — 別 PR のマージで行数と件数がずれた 1 件、指していた関数がファイルごと別ファイルへ移った 1 件、行番号が全部ずれた 1 件。生き残った 1 件は `import` 文というファイル冒頭付近を指していた)。

問題は腐ること自体ではなく、**腐り方の質**である。**行番号は無言でずれる** — ずれた先には別のコードがあり、executor はそこを正しい場所だと信じて直す。**シンボル名は失敗が可視化される** — 関数名・定数名・テスト名は、無くなっていれば grep で見つからない。

- **位置はシンボル名で指し、行番号は括弧で補助する。** 「`state-transitions.ts` の `applyInReview` (538 行)」。行番号は読み手が最初に飛ぶための便宜であって、位置の正ではない。Markdown を指すときは見出しが同じ役割を果たす (「`### in-review` の『効果:』の記述」)。
- **受け入れ条件には行番号を書かない。** verifier は受け入れ条件を実装後の最終状態に直接照合するので、ここが腐ると正しく実装されたものを FAIL にする。条件はシンボル名・見出し・コマンドの出力で書く。
- **行番号や実測値を本文に書いたら `裏取り時点: <sha>` を添える** (書式はトラッカー別: references/trackers/)。読み手が `git diff <sha> HEAD -- <パス>` で腐りの有無を機械的に判定できるようになる。gate 宣言で記録する sha と同じ 1 行で兼ねてよい。
- **受け入れ条件の絶対数は行番号より危険である。** 「テスト総数が 184 件を下回らない」型の閾値は、書いた時点の数字がそのまま基準になる。実装までに件数が増えていれば、その差だけ退行を見逃す (実測: 184 と書かれた条件が、実装時点の 194 件に対して 10 件の削減を許す状態になっていた)。絶対数には `裏取り時点:` を必ず添え、深掘りのたびに測り直す。

## 粒度

**executor 1 体が research → plan → implement → report を同一コンテキストで 1 回通せるサイズ。** 目安:

- 変更が 1 つの計画としてファイル単位で書き下せて、受け入れ条件が 1 回の実装でまとめて満たせるなら、1 issue。
- 受け入れ条件が「独立して出荷できる複数の束」に自然に割れるなら、大きすぎる。分割して依存を張る。
- 逆に、受け入れ条件 1 つのために issue を割るのは細かすぎる (1 issue には 4 フェーズ + 検証の固定コストがかかる)。

## gate 宣言 (light)

task-pipeline は既定で 4 フェーズをそれぞれ検証ゲート付きで回す。次の **2 軸を両方**満たす issue に限り、gate 宣言を付けてよい。**表現はトラッカー別** (references/trackers/):

- **gh**: ラベル `gate-light` を付ける (`ready` / `pending-deps` と併存する独立軸。ラベルは全置換なので既存ラベルごと計算すること)
- **markdown**: アイテムファイル本文の末尾に、このマーカー行をそのまま 1 行で入れる

```
<!-- task-pipeline:gate=light -->
```

gh で本文マーカーを使わないのは、アダプタの本文転記が実際にこれを落として宣言のあるタスクが静かに full で回ったため (実測 2/3 欠落、`task-pipeline/docs/gate-declaration-2026-08.md`)。ラベルは構造データとして届くので転記に依存しない。どちらのトラッカーでも、アダプタが宣言をタスクファイルの frontmatter (`gate: light`) に転写し、パイプラインはその 1 行だけを見る。

gate: light を付与すると判断した時点 (下記の仕様軸・リスク軸を両方満たすと確認した時点) で、`git -C <target project> rev-parse HEAD` を実行し、その値を issue 本文に記録する。書式はトラッカー別 (references/trackers/)。これは 2 軸の判定そのものではなく、判定の根拠にした裏取り時点を機械照合可能な形で残すための必須の追加記録であり、sha 記録の無い gate: light 宣言は不完全とみなす。記録した sha は実際に task-pipeline 側で読まれる — **executor** が引き継ぎ判定 (`references/executor.md` の「引き継ぎ」節) で `git diff <sha> HEAD -- <パス>` の空判定に使い、**verifier** が同じ diff を自分で再実行して確かめる (`references/verifier.md` の research 節)。したがって **sha の正確さ (裏取り時点の HEAD と一致していること) が、以降の再検証省略の可否を直接左右する** — 誤った sha を記録すると、間違った引き継ぎの根拠になる。**既存の (sha未記録の) gate: light issue に遡って追記は求めない** — 対象は今後新規に gate: light を付与する issue のみ。

1. **仕様軸**: ready 基準 1 を満たす — 要求のすべてが機械検証可能な受け入れ条件に覆われている。
2. **リスク軸**: 実装が「どの入力がどの帰結 (受理、拒否、分岐先、エラー) になるか」の割り当てを変えず、そのような判定の新設も無い (純リファクタ、性能改善、文言だけの変更、ドキュメント等)。判定の入力は引数に限らず、判定が見るものすべて (データ、ファイルや環境の状態) を含む。判定を変える・新設する issue には付けない — 仕様が固くても、判定を変えるタスクでは検証ゲートが最高価値の欠陥 (バグがあっても緑になる回帰テスト設計) を実際に捕まえている (task-pipeline/docs/cost-analysis-2026-07.md §6)。

**リスク軸の判定例**: `tests/` と `docs/` だけを触る変更は原則リスク軸を満たす (アサーションの追加、テストメソッドの分割、命名や記法の統一、setUp のフィクスチャ集約、ドキュメントの修正)。`src/` の分岐や検証を足す・変える変更は満たさない。**この例はリスク軸だけの話で、仕様軸は別に判定する** — `tests/` だけを触る issue でも、受け入れ条件が「掃除する」程度にしか書けていないなら仕様軸で落ちる。

この例を置いたのは、実測で**適格な 4 件のうち 2 件しか宣言できていなかった**ため (RayDiContext 2026-08-01: #79 / #80 には付き、#81 / #82 には付かなかったが、後者の PR は #93 が `tests/` 5 ファイル、#94 が `tests/` 9 ファイル + `docs/decisions.md` で、どちらも `src/` を 1 行も触っていない)。「割り当てを変えない」だけでは、テストを触る変更がどちらに転ぶかを読み手が決められなかった。

宣言があると task-pipeline は research と plan を 1 フェーズに統合し、検証ゲートを 1 回減らす。宣言の妥当性は統合ゲートの verifier が再判定する — 覆されると full 相当の要求 (テスト網羅の最低ラインを含む) で判定され、網羅を欠く plan は FAIL になる。往復が増えるだけで安くならない。**迷ったら付けない** (宣言なしの既定は現行どおりの 4 ゲートで、常に安全側)。

## risk-high 宣言

gate 宣言が「検証を減らしてよい」側の事前評価であるのに対し、`risk-high` は**「間違えたときの損害が大きいので、実装と検証をより強い側に振ってよい」宣言**である。gate 宣言と同じく**深掘りの裏取りをした時点で判定する** — 実装時点では「何に触るか」がもう決まっていて、判定をやり直す材料が薄い。**表現はトラッカー別** (references/trackers/):

- **gh**: ラベル `risk-high` を付ける (`ready` / `pending-deps` / `gate-light` / `priority-*` と併存する独立軸。ラベルは全置換なので既存ラベルごと計算すること)
- **markdown**: アイテムファイル本文の末尾に、このマーカー行をそのまま 1 行で入れる

```
<!-- task-pipeline:risk=high -->
```

gh で本文マーカーを使わない理由は gate 宣言と同じ (アダプタの本文転記が末尾マーカー行を実際に落とした。実測 2/3 欠落、`task-pipeline/docs/gate-declaration-2026-08.md`)。どちらのトラッカーでも、アダプタが宣言をタスクファイルの frontmatter (`risk: high`) に転写し、パイプラインはその 1 行だけを見る。

gate 宣言が 2 軸の AND なのに対し、**こちらは 1 軸で、次の 6 つのいずれか 1 つでも当てはまれば `risk-high`** である:

1. **公開 API・エクスポート契約の変更** — 外部から呼ばれる名前・シグネチャ・戻り値の形が変わる。
2. **スキーマ・データ移行** — 永続データの形が変わる、または既存データを書き換える。
3. **セキュリティ経路** — authn/authz、暗号、入力検証。
4. **並行性・ロック** — 同時実行の順序や排他が結果を変えうる。
5. **複数モジュールにまたがる血流域** — 1 箇所の変更が離れた場所の帰結を変える。
6. **新規依存の導入** — 依存を 1 本足す。

**判定例**: `src/` の export されたシンボルのシグネチャや戻り値の形を変えるなら 1 (内部だけで呼ばれる補助関数の付け替えは当たらない)。マイグレーションや既存レコードを書き換える処理を足すなら 2 (読み取りだけのクエリ追加は当たらない)。ログイン・トークン検証・権限判定・入力バリデーションの中身に触るなら 3 (それらを呼ぶ側の文言変更は当たらない)。ロック・トランザクション境界・待ち合わせ・共有状態の書き込み順に触るなら 4。変更が複数のモジュールにまたがり、**かつ**呼び出し関係で繋がっていて片方だけ直すと壊れるなら 5 (同じ機械的変更を横に並べて適用するだけの一斉置換は当たらない — 血流域とは離れた場所の帰結が変わることである)。依存宣言ファイルに新しい依存を足すなら 6 (既存依存のバージョン上げは、1〜5 のどれかに当たらない限り当たらない)。**`tests/` と `docs/` だけを触る変更は、どの項にも当たらない。**

この例を初日から置くのは、gate 宣言のリスク軸で**基準文だけでは読み手が境界を決められなかった実測がある**ため (適格な 4 件のうち 2 件しか宣言できていなかった。上記「gate 宣言 (light)」の判定例の由来)。同じ形の軸を例なしで足せば、同じように発火しない。

書き方の規律:

- **`gate-light` と `risk-high` は背反である。** gate 宣言のリスク軸は「判定の割り当てを変えず、判定の新設も無い」であり、上の 6 項目はいずれもその条件を破る。**両方付いている issue は、どちらかの判定が誤っている** (パイプライン側は保守側に倒して high を採るので実行は壊れないが、宣言としては誤りなので棚卸し手順 4 で拾う)。
- **sha (`裏取り時点:`) は要求しない。** gate 宣言が sha を必須にするのは、research の再検証を省く根拠にするからである (上記「gate 宣言 (light)」)。`risk-high` は検証を省かず足す方向にしか効かないので、判定が腐っても安全側にしか外れない。行番号や実測値を本文に書いたときの sha は、宣言とは無関係に従来どおり要る (上記「位置参照と数値」)。
- **規模 (size) の軸は作らない。** 粒度は上記「粒度」が「1 サイクルで通せるサイズ」に正規化済みで、超えているものの正しい出力は宣言ではなく**分解**である。宣言で大きさを申告できるようにすると、分解すべきものが宣言付きで通ってしまう。
- **宣言もこの skill の書き込みなので、承認を経る** (下記「承認と書き込み」の手順 1-2)。結果セットに「どの issue に付けるか、当たる項の番号 1 つ以上」を含める。**人間承認がこの宣言の唯一のゲートである** — パイプライン側にこれを再判定する経路は無い。
- **迷ったら付けてよい** (上振れは実装と検証を強くする方向にしか効かない)。ただし**候補の多数派が `risk-high` になっているなら、軸として機能していない** — 6 項目のどれに当たるかを言えないものには付けない。

宣言があると task-pipeline は実装側・検証側の provider と model をより強い側に選ぶ (`task-pipeline/playbooks/agent-launch.md`)。**フェーズ列とゲートの数は変わらない** — 宣言なしと同じ 4 フェーズ 4 ゲートである (減らすのは `gate-light` だけの役目)。

## 優先度

task-pipeline は承認候補を優先度で 3 段に分け、**段をまたぐ並べ替えをしない** (段の中だけをトリアージが並べる)。段を作るのはこの skill である。表現はトラッカー別 (references/trackers/) で、gh はラベル `priority-high` / `priority-low`、無指定が中位。

段を決める基準:

- **high**: 他の issue を解放する (依存元である)、実害の出ている欠陥やリスクを消す、放置するとコストが増える (他の変更と競合する / 前提が腐る)、外部に期限がある — のいずれか。
- **low**: 単独で完結して後続が無く、遅らせても損失が小さい。整理・掃除の類で、今やる理由が「気になるから」に留まるもの。
- **無指定 (既定)**: 上のどちらでもないもの。**これが多数派になるのが正常である。**

書き方の規律:

- **既定は無指定。** 段は「他より先に出したい理由が言えるか」で付けるものなので、**候補の半分が `high` になっているなら、それは段として機能していない**。付けた理由は issue 本文の背景から読み取れる状態にしておく (ラベルは結論で、根拠は本文にある)。
- **優先度もこの skill の書き込みなので、承認を経る** (下記「承認と書き込み」)。結果セットに「どの issue にどの段を付けるか、その理由 1 行」を含める。
- **ユーザーが手で付けた段は無断で変えない。** 変えるべきだと判断したら、現在の値と変更案の両方を結果セットに出して承認を求める。この skill が付けた段を後から見直すのは自由 (深掘りで前提が変わることはある)。
- 依存で待たされている issue に `high` を付けても意味は無い (候補に現れないので段が効かない)。**昇格させるときに、そこで初めて段を判断する**のが実際に効く順序である。

## 依存

- 依存とは「この issue の実装が、別 issue の成果 (マージ/受け入れ済みの状態) を前提にする」こと。後の issue の受け入れ条件が前の issue の成果の上でしか成立しないなら、それは依存である。
- issue 本文に 1 行で書く: `依存: <参照>, <参照>` (gh は `#番号`、markdown は id)。依存が無いなら書かない。この行は昇格スキャンが機械的に読む唯一の手掛かりなので、書式を崩さない。
- **ゲート**: task-pipeline は依存という概念を持たず、候補を承認順に実行するだけである。だから「依存が解けていない issue は候補に見えない」ことをこちらが保証する。ready の表現 (gh: `ready` ラベル、markdown: リスト掲載) がそのままゲートになる — 依存がすべて Done になるまで ready にしない。in_review では足りない (レビュー前の成果に次を積まない。`finish=pr` ではブランチ上にしか存在しない)。markdown のゲートは構造的 (リスト未掲載はアダプタが見ない) だが、**gh のゲートはパイプラインを `?label=ready` 付きで起動することにかかっている** — フィルタなしの `/loop /task-pipeline gh` では未準備・依存待ちの issue も候補に入ってしまうので、接続コマンドの案内で必ず付ける。
- **昇格**: 起動のたびに依存待ちの issue を走査し、依存がすべて Done になり、かつ未確定が残っていないものを ready に上げて、上げた分を報告する。昇格は承認を取らずに行ってよい (task-pipeline 側に 1 件ずつの承認ゲートが既にあり、二重承認は無意味)。ただし依存が「やらない」として閉じられていた場合は解決ではない — 昇格させず、従属 issue の扱い (前提が消えた) をユーザーに上げる。

## 調査

分解も深掘りも、**実際のコードベースを調べてから書く**。影響範囲、既存の実装、似たものが既に無いか、既存 open issue との重複。調べずに切った分解はこの skill の価値の大半を失う。

- 独立した調べ物はサブエージェント (read-only) に並列で投げてよい。本当に独立なものだけにすること。
- トラッカーの生データや MCP ツールスキーマをメインコンテキストに積みたくない操作は、サブエージェントに references/trackers/<tracker>.md の**パスを渡して**任せる (指示本文をプロンプトに書き写さない)。ただしこの skill は 1 回の対話で完結するので、task-pipeline ほどの規律は要らない — 判断はこちら。
- 調査で判明した事実が要望の前提と食い違うときは、黙って辻褄を合わせず、食い違いをそのままユーザーに見せる。
- 重複が見つかったら、新規作成ではなく既存 issue の深掘り (または統合の提案) に切り替える。同じことを言う issue を増やすのはこの skill の逆の仕事である。

## 人間にしか答えられない問い

仕様の選択、優先順位、外部との約束、ユーザーの好み — これらは調査では解けない。**推測で埋めて issue に書くことを、この skill は最悪の失敗とみなす** (間違った仕様のまま自動実装まで走り切るため)。「調べれば分かるか」ではなく「答えを決める権限が誰にあるか」で判定する。

- ユーザーに聞ける場面なら、質問は溜めてからまとめて聞く (AskUserQuestion)。小出しにしない。
- 答えが得られないまま issue を書くなら、本文に `未確定: <問い>` の行を 1 問 1 行で残し、その issue は ready にしない。答えが出たら行ごと消す (この行の有無を昇格スキャンが機械的に見る)。勝手に決めた値を仮置きして未確定を消すのは、未確定を残すより悪い。

## 棚卸し (入力なし)

`/task-prep gh` のように入力を省いたときは、**トラッカー全体を 1 回見て、次に手を入れるべき場所を出す**。1 件を指定して深掘りするには「どれを深掘りすべきか」を先に知っている必要があり、それを知る手段がこれである。

1. 昇格 (下記「依存」) を先に済ませる。上げた分は報告に含める。
2. open なアイテム (markdown ならバックログ本体・`## In Review` に掲載されている行) を列挙し、**実行中のものを除く**: パイプラインが書いた状態の表現が付いているもの。表現はトラッカー別 (references/trackers/) — **gh**: パイプラインの状態ラベル (`in-review` / `blocked`) が付いているもの、assignee が付いているもの、PR が紐付いているもの。**markdown**: バックログ本体の行に `(wip)` / `(blocked: ...)` の suffix が付いているもの、および `## In Review` セクションに掲載されているもの (`references/trackers/markdown.md` の状態表)。それらは task-pipeline の領分で、こちらが本文を書き換えると走行中のタスクの足元が変わる。
3. 残りを **ready 基準 5 項目に照らし、欠けている基準を issue ごとに 1 行**で出す。典型的な欠けは次の 5 つ:
   - 受け入れ条件が第三者判定できない (「掃除する」「整理する」で終わっている)
   - 本文が裏取りされていない (実在しないパス・関数名・行番号を指している)
   - `未確定:` が残っている (人待ち。**これは欠陥ではない** — 誰の答え待ちかを添える)
   - 粒度が 1 サイクルを超える (分解の候補)
   - 依存が未解決、または依存先が `not_planned` で閉じている (前提が消えている)
4. **横断でしか見つからないものも出す**: 重複と包含関係、`ready` と `pending-deps` の同時付与、`依存:` 行の書式崩れ (昇格スキャンが読めない)、gate 宣言の 2 軸を満たすのに宣言が無いもの、**`gate-light` と `risk-high` の同時付与** (背反なのでどちらかの判定が誤っている)、**優先度の段の付き方** (`high` が候補の半分を超えていないか、依存待ちの issue にだけ `high` が付いていないか)。1 件ずつ見ていては出てこないので、棚卸しの主目的はむしろこちらである。
5. 報告は**次の行動の一覧**にする — 深掘りすべき id、分解すべき id、人の判断を待っている id、統合すべき組。ユーザーが 1 つ選んだら、そのまま該当の入口 (深掘り / 分解) に入る。トラッカー側に次の行動が無いなら (全 issue が実行中・レビュー待ち・既にきれい)、それをそのまま報告して `/task-scout` を案内する (引数はこの棚卸しと同じ tracker と source) — まだ issue になっていないものをコードベースから探すのは棚卸しの範囲外である。
6. **書き込むのは昇格だけ。** ラベルの付け替え・本文の修正・重複の close はすべて提案で止める (実行するなら深掘りの入口に入り直すのが正しい経路で、そこには承認ゲートがある)。

- 本文の精査は **read-only サブエージェントに分担させる** (1 体あたり数件、並列)。棚卸しでメインコンテキストを食い潰すと、続けて深掘りに入れなくなる — この skill の出口は常に「次の 1 件に手を入れる」ことなので、そこに辿り着けないなら棚卸しは失敗である。
- **規模のガード**: 精査対象が 30 件を超えるなら全件は見ない。状態別の集計を出したうえで、精査は `ready` と `pending-deps` に絞り、残りは件数と id だけ報告する。**絞ったことを必ず明示する** (黙って上位だけ見ると「全部見た」と読まれる)。

## 承認と書き込み

トラッカーへの書き込み (issue 作成・本文更新) は外向きで、消しにくい。書き込む前に必ず:

1. 結果セットを提示する — 各 issue のタイトル、範囲 1 行、依存関係、残った未確定の問い、そして**書き込み先** (gh ならリポジトリ名)。深掘り 1 件なら更新後の本文そのもの。既存 issue を分解したときは、元 issue の処置 (子への参照を残して close する / リストから外す) と、**元 issue に依存していた issue の `依存:` 行の子への張り替え**も結果セットに含める (張り替え漏れは「前提が消えた」エスカレートになって返ってくる)。
2. 明示的な承認を得る。承認された分だけ書き込む (手順はトラッカー別: references/trackers/<tracker>.md を読んで従う)。依存先が承認されなかった issue はその回では作らず、依存ごと見直して再提示する。
3. 書き込み後、何を書き込みどれを ready にしたかを報告し、ready が 1 件以上あるときだけ接続コマンド 1 行 (例: `/loop /task-pipeline gh ?label=ready finish=pr`) を添える。

## 報告規律

Before reporting progress, audit each claim against a tool result from this session. Only report work you can point to evidence for; if something is not yet verified, say so explicitly. 裏取りに使った証拠 (ファイルパス・コマンド出力) は issue 本文とレポートの双方から指せる状態にしておく。

# task-prep — 要望を task-pipeline の入力に変える

あなたは task-pipeline の**上流**である。出力 (issue 本文) の読み手は人間だけではなく、task-pipeline の executor と verifier である。verifier は最後の report フェーズで、計画を経由せず **issue 本文の要求を実装後の最終状態に直接照合する**。この skill の合否は、書いた issue がその照合に耐えるかで決まる。曖昧な issue は検証 FAIL の連発か、もっと悪ければ「それらしい何か」の自動実装に化ける。

ユーザーの仕事を「やりたいことを口に出す」「人間にしか答えられない問いに答える」「承認する」「レビューする」の 4 つに絞ることがゴールである。それ以外 (調査・分解・裏取り・依存整理・文面化) はすべてこちらの仕事。

## 入口

`$ARGUMENTS`: `<tracker> [source] <入力>`。source の意味は task-pipeline と同じ (`gh` は省略でカレントリポジトリ、`markdown` はリストファイルのパス) だが、切り分けは違う — **tracker 直後のトークンが source の形 (markdown: パス、gh: `owner/repo`) のときだけ source として取り、残りはすべて入力**。入力の形で入口を選ぶ:

- **要望テキスト** (「認証まわりを直したい」等) → 分解
- **issue 参照** (`#42` / issue URL / markdown の id) → 深掘り
- **入力なし** → 昇格と状況報告だけして終わる

分解と深掘りは一方通行ではない。分解で生まれた各 issue は ready 基準まで深掘りしてから書き込む。深掘りの途中で 1 サイクルに収まらないと分かったら分解に切り替える。既に立っている大きすぎる issue の参照を渡されたら、それは「その issue を分解する」依頼である。

どの入口でも、最初に昇格 (下記「依存」) を済ませてから本題に入る。

## ready 基準 (この skill の合否条件)

issue は次をすべて満たすとき、そのときだけ ready (task-pipeline の候補) にできる:

1. **第三者判定可能**: 実装完了後に、その issue しか読んでいない第三者が、要求を満たしたかを PASS / FAIL で判定できる。要求はすべて、コマンドか観測で判定できる受け入れ条件に覆われている。
2. **裏取り済み**: 本文中のファイルパス・関数名・現状挙動は、実際のコードで確認してから書いてある。確認できなかった記述を、確認できたものと同じ調子で書いていない (未検証と明記するか、削る)。間違った現状認識は自動実装をまっすぐ間違った方向へ走らせる。
3. **人間の問いが残っていない**: 本文に `未確定:` 行 (下記) が残っていない。
4. **粒度が 1 サイクル**: 下記「粒度」に収まる。
5. **依存ゼロ**: 依存する issue がすべて Done (マージ/受け入れ済み) である。本文が完成していても、依存が残るなら ready にせず依存待ちとして記録する (表現はトラッカー別: references/trackers/)。

本文の形式は固定しない。ただし、要求と受け入れ条件が区別して読めること、`依存:` と `未確定:` は下記の書式で書くこと (機械的に走査するため)。

## 粒度

**executor 1 体が research → plan → implement → report を同一コンテキストで 1 回通せるサイズ。** 目安:

- 変更が 1 つの計画としてファイル単位で書き下せて、受け入れ条件が 1 回の実装でまとめて満たせるなら、1 issue。
- 受け入れ条件が「独立して出荷できる複数の束」に自然に割れるなら、大きすぎる。分割して依存を張る。
- 逆に、受け入れ条件 1 つのために issue を割るのは細かすぎる (1 issue には 4 フェーズ + 検証の固定コストがかかる)。

## gate 宣言 (light)

task-pipeline は既定で 4 フェーズをそれぞれ検証ゲート付きで回す。次の **2 軸を両方**満たす issue に限り、本文の末尾にこのマーカー行をそのまま 1 行で入れてよい (gh は issue 本文、markdown はアイテムファイル。アダプタが本文ごとタスクファイルに転記する):

```
<!-- task-pipeline:gate=light -->
```

1. **仕様軸**: ready 基準 1 を満たす — 要求のすべてが機械検証可能な受け入れ条件に覆われている。
2. **リスク軸**: 実装が「どの入力がどの帰結 (受理、拒否、分岐先、エラー) になるか」の割り当てを変えず、そのような判定の新設も無い (純リファクタ、性能改善、文言だけの変更、ドキュメント等)。判定を変える・新設する issue には付けない — 仕様が固くても、判定を変えるタスクでは検証ゲートが最高価値の欠陥 (バグがあっても緑になる回帰テスト設計) を実際に捕まえている (task-pipeline/docs/cost-analysis-2026-07.md §6)。

宣言があると task-pipeline は research と plan を 1 フェーズに統合し、検証ゲートを 1 回減らす。宣言の妥当性は統合ゲートの verifier が再判定する — 覆されると full 相当の要求で FAIL が返り、往復が増えるだけで安くならない。**迷ったら付けない** (宣言なしの既定は現行どおりの 4 ゲートで、常に安全側)。

## 依存

- 依存とは「この issue の実装が、別 issue の成果 (マージ/受け入れ済みの状態) を前提にする」こと。後の issue の受け入れ条件が前の issue の成果の上でしか成立しないなら、それは依存である。
- issue 本文に 1 行で書く: `依存: <参照>, <参照>` (gh は `#番号`、markdown は id)。依存が無いなら書かない。この行は昇格スキャンが機械的に読む唯一の手掛かりなので、書式を崩さない。
- **ゲート**: task-pipeline は依存という概念を持たず、候補を承認順に実行するだけである。だから「依存が解けていない issue は候補に見えない」ことをこちらが保証する。ready の表現 (gh: `ready` ラベル、markdown: リスト掲載) がそのままゲートになる — 依存がすべて Done になるまで ready にしない。in_review では足りない (レビュー前の成果に次を積まない。`finish=pr` ではブランチ上にしか存在しない)。markdown のゲートは構造的 (リスト未掲載はアダプタが見ない) だが、**gh のゲートはパイプラインを `?label=ready` 付きで起動することにかかっている** — フィルタなしの `/loop /task-pipeline gh` では未準備・依存待ちの issue も候補に入ってしまうので、接続コマンドの案内で必ず付ける。
- **昇格**: 起動のたびに依存待ちの issue を走査し、依存がすべて Done になり、かつ未確定が残っていないものを ready に上げて、上げた分を報告する。昇格は承認を取らずに行ってよい (task-pipeline 側に 1 件ずつの承認ゲートが既にあり、二重承認は無意味)。ただし依存が「やらない」として閉じられていた場合は解決ではない — 昇格させず、従属 issue の扱い (前提が消えた) をユーザーに上げる。

## 調査

分解も深掘りも、**実際のコードベースを調べてから書く**。影響範囲、既存の実装、似たものが既に無いか、既存 open issue との重複。調べずに切った分解はこの skill の価値の大半を失う。

- 独立した調べ物はサブエージェント (read-only) に並列で投げてよい。本当に独立なものだけにすること。
- トラッカーの生データや MCP ツールスキーマをメインコンテキストに積みたくない操作は、サブエージェントに references/trackers/<tracker>.md の**パスを渡して**任せる (指示本文をプロンプトに書き写さない)。ただしこの skill は 1 回の対話で完結するので、task-pipeline ほどの規律は要らない — 判断はこちら。
- 調査で判明した事実が要望の前提と食い違うときは、黙って辻褄を合わせず、食い違いをそのままユーザーに見せる。
- 重複が見つかったら、新規作成ではなく既存 issue の深掘り (または統合の提案) に切り替える。同じことを言う issue を増やすのはこの skill の逆の仕事である。

## 人間にしか答えられない問い

仕様の選択、優先順位、外部との約束、ユーザーの好み — これらは調査では解けない。**推測で埋めて issue に書くことを、この skill は最悪の失敗とみなす** (間違った仕様のまま自動実装まで走り切るため)。「調べれば分かるか」ではなく「答えを決める権限が誰にあるか」で判定する。

- ユーザーに聞ける場面なら、質問は溜めてからまとめて聞く (AskUserQuestion)。小出しにしない。
- 答えが得られないまま issue を書くなら、本文に `未確定: <問い>` の行を 1 問 1 行で残し、その issue は ready にしない。答えが出たら行ごと消す (この行の有無を昇格スキャンが機械的に見る)。勝手に決めた値を仮置きして未確定を消すのは、未確定を残すより悪い。

## 承認と書き込み

トラッカーへの書き込み (issue 作成・本文更新) は外向きで、消しにくい。書き込む前に必ず:

1. 結果セットを提示する — 各 issue のタイトル、範囲 1 行、依存関係、残った未確定の問い、そして**書き込み先** (gh ならリポジトリ名)。深掘り 1 件なら更新後の本文そのもの。既存 issue を分解したときは、元 issue の処置 (子への参照を残して close する / リストから外す) と、**元 issue に依存していた issue の `依存:` 行の子への張り替え**も結果セットに含める (張り替え漏れは「前提が消えた」エスカレートになって返ってくる)。
2. 明示的な承認を得る。承認された分だけ書き込む (手順はトラッカー別: references/trackers/<tracker>.md を読んで従う)。依存先が承認されなかった issue はその回では作らず、依存ごと見直して再提示する。
3. 書き込み後、何を書き込みどれを ready にしたかを報告し、ready が 1 件以上あるときだけ接続コマンド 1 行 (例: `/loop /task-pipeline gh ?label=ready finish=pr`) を添える。

## 報告規律

Before reporting progress, audit each claim against a tool result from this session. Only report work you can point to evidence for; if something is not yet verified, say so explicitly. 裏取りに使った証拠 (ファイルパス・コマンド出力) は issue 本文とレポートの双方から指せる状態にしておく。

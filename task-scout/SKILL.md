# task-scout — コードベースの実査から次の候補を出す

あなたは task-prep のさらに上流である。task-prep の棚卸しが見るのは**トラッカーに既にある issue** の欠陥だが、この skill が探すのは「まだ issue になっていない、コードベースを読めば見えてくるやるべきこと」である。出すのは**決定の手前まで** — 候補と根拠と順位を出し、選ぶのはユーザー。

この線引きは意図的である。下流には検証ゲート・CI・レビューがあるので、間違ったものが黙って入ることは起きない。希少なのは正しさではなく**ユーザーのレビュー時間**で、それを何に使うかはユーザーが決める。だからこの skill はトラッカーに一切書き込まない。

## 入口

`$ARGUMENTS`: `<tracker> [source]`。意味は task-prep と同じ (`gh` は省略でカレントリポジトリ、`markdown` はリストファイルのパス)。実査の対象はカレントプロジェクトで、プロジェクトルートは task-pipeline と同じ規則で決める — `git rev-parse --path-format=absolute --git-common-dir` が返すパスの親 (メイン worktree のルート)。linked worktree から起動されても実行記録が分散しないためで、git リポジトリでなければカレントディレクトリでよい。

使いどころは「ready が尽き、かつ open issue 側に深掘り・分解すべきものが残っていない」とき。既存 issue の欠陥を洗って次の一手を出すのは task-prep の棚卸しの領分で、そちらで足りるならこの skill の出番ではない。

## 読むもの

推測で書かない。候補の土台は、次をすべて実際に読んでから:

- **前回の実行記録** (下記) — 最初に読む。
- **コードベース全体** — read-only サブエージェントに領域を分担させ、メインコンテキストに載せるのは構造化された要約だけにする。メインを食い潰すと出口で task-prep に続けて入れなくなり、この skill は失敗である。
- **CLAUDE.md** — 規約、テストの走らせ方、禁止事項。
- **docs/decisions.md** — あれば必読。「意図的にそうしている、戻すな」と「コストが見合わないので見送った」の記録で、ここで決着している話を蒸し返す候補はそれだけで的外れ。無いリポジトリでは、決定の記録が別の場所にあると分かるなら (docs/ 配下の設計メモ等) それを同じ目的で読み、何も無ければ**報告に 1 行「見送り・意図の記録との照合はしていない」と明示する**。代わりの情報源を探し回りはしない。
- **open issue 全部** — 重複する候補を出さないため。トラッカーへの到達手段 (使うツール、source の解釈) は task-prep の `references/trackers/<tracker>.md` に従うが、**使うのは読み取りだけ** — そこに書かれた書き込み操作はこの skill では決して使わない。列挙の操作がそこに定義されていなくても、同じ到達手段で open issue の一覧と本文を読む (取得物をローカルへ書き出すなら `.task-scout/` 配下)。件数が多ければ読み込みと要約もサブエージェントに分担させ、読み切れずに絞ったなら**絞ったことを報告に明示する**。
- **直近 1〜2 週間のマージ履歴** — 何が動いている最中かを掴む。

独立した調べ物は read-only サブエージェントに並列で投げ、待つ間も自分の作業を進める。サブエージェントが的を外している・文脈が足りないと分かったら介入する。

## 候補の基準

次に着手する価値のある候補を**多くて 8 件**。数を埋めることが目的ではない — 根拠の弱いものを足すくらいなら 3 件でよい。種類は問わない (欠陥やリスクの解消、保守性、新機能、開発体験)。各候補に短い kebab-case の slug を付け (実行記録と引き継ぎで候補を指すため)、次を書く:

1. **何をするか** — 1〜2 文
2. **なぜ今か** — 何が困っているのか、放置するとどうなるのか。ここが弱い候補は落とす
3. **裏取り** — 主張の根拠になるファイルパス・行番号・コマンドの実出力。「テストが遅い」ではなく「`composer tests` が 12.4 秒で、うち 8.1 秒が `BinCompileTest`」のように
4. **受け入れ条件の案** — その issue しか読んでいない第三者が PASS / FAIL を判定できる形 (task-prep の ready 基準 1)。書けない候補は、**書けないという事実ごと出す** (ユーザーの判断が要る印である)
5. **規模** — task-pipeline の 1 サイクルに収まるか。超えるなら分割案
6. **依存** — 他の候補や既存 issue に依存するか

最後に順位を付け、**推薦を出す**。網羅的な比較表ではなく「私ならこの順でやる」と理由を。

提示する前に、裏取りとして書いた行番号・コマンド出力を**フレッシュなサブエージェントに再確認させる**。調査した本人の evidence は経験上ここで崩れる。長く走るなら、提示直前だけでなく区切りごとにも同じ確かめ方を回す。

## 境界 (やらないこと)

- **トラッカーに書き込まない。** issue の作成・本文更新・ラベル・コメント、すべて。task-prep と違い、この skill には「承認を得て書き込む」経路そのものが無い。
- **実装しない。作業ツリーを変えない。** 書いてよいのは `.task-scout/` と、その除外登録 (下記) だけ。
- **decisions.md で決着した話を蒸し返さない。** 蒸し返す価値があると考えたなら、その判断が書かれた時点から何が変わったのかを先に示す。
- **既存 issue と重なる候補を新規として出さない。** 重なりに気づいたら issue の参照を挙げて「これを深掘りすべき」として出す。

## 前回の実行記録

`<プロジェクトルート>/.task-scout/log.md`。初回作成時に `<git common dir>/info/exclude` へ `/.task-scout/` を追記する (未記載のときだけ。task-pipeline の `.task-pipeline/` と同じ扱い)。目的は、**却下された候補を毎回出し直してユーザーに同じ判断を繰り返させない**こと。

- 実行の最後 — 引き継ぐ場合は /task-prep を起動する**前** — に追記する: 日付と、出した候補それぞれ 1 行 (slug と主張の要約) + 帰結 — 引き継いだ / 却下 (理由が言われたなら添える) / 判断なし。候補を提示して選択を待つ時点で暫定 (全件「判断なし」) を書いておき、帰結が付いたら更新してよい — 提示後に会話が途切れても記録が残る。
- 次回の実行はこれを最初に読む。**却下された候補は、却下理由の前提が変わったのでなければ出し直さない**。出し直すなら何が変わったかを添える (decisions.md と同じ規律)。判断なしのまま流れた候補は再登場してよいが、「前回も提示」と明示する。

## 出口 (task-prep への引き継ぎ)

ユーザーが候補から 1 件選んだら、同じセッションで /task-prep を起動する (Skill tool。引数はこの skill が受け取ったのと同じ `<tracker> [source]` に入力を続けたもの)。入力は候補の種類で変える:

- 既存 issue の深掘りを推す候補 → **issue 参照**をそのまま渡す (task-prep の深掘り入口に入る)。
- それ以外 → **自己完結の要望文**に整形して渡す。含めるのは: 何をするか、なぜ今か、裏取り (パス・行番号・実出力)、受け入れ条件の案、規模、依存。**別の会話に渡っても通じる文章として書く** — この skill の調査は task-prep の調査の代わりにはならず、task-prep は通常どおり裏取りを検証し直し、承認を経て書き込む。

ユーザーが「今は選ばない」「別セッションでやる」なら、渡すはずだった入力 (要望文 / issue 参照) をそのままコピペできる形で示して終える。どちらの場合も実行記録は書く。

## 報告規律

Before reporting progress, audit each claim against a tool result from this session. Only report work you can point to evidence for; if something is not yet verified, say so explicitly.

候補の提示は、この会話を見ていない読み手にも通じる文章で書く。結論 (何件出したか、推薦はどれか) を最初に置き、調査中に作った略語や記号の連鎖を持ち込まない。

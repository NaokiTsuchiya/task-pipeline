# review-catalog — レビュー観点の言語化と運用

人間レビューが担っていた確認を、判定可能な「行」の集合に変換して維持する。各行は「何を・誰が・どう判定し・何をもって合格とするか」を固定する。原則:

- 判定は **deterministic > agent > human** の順に、置けるだけ機械側へ置く。
- `check: human` の行は自動化ギャップの台帳であり、常に一覧可能に保つ。
- rubric に曖昧語 (「適切に」「必要に応じて」) を書かない。書けないなら `check: human`。

## ファイル

| ファイル | 内容 |
|---|---|
| `references/layers.md` | 5 層モデル。行の追加・分類・昇格の前に必ず読む |
| `references/catalog.yaml` | 共通カタログ (L0/L1 行、L2 bindings、L3 行)。全プロジェクト共有 |
| `references/project-template.yaml` | プロジェクトファイルの雛形 |
| `<project>/docs/review-catalog.yaml` | プロジェクトファイル (L4 行 + params + overrides のみ)。`docs/` が無ければルート直下 |

## 行スキーマ

| field | 内容 |
|---|---|
| `id` | 安定識別子。層接頭辞 (`L0-`, `L3-`, プロジェクト行は `P-`) |
| `layer` | L0〜L4 (`references/layers.md`) |
| `statement` | 守るべきことを 1 文で |
| `check` | `deterministic` (ツール) / `agent` (AI レビュア + rubric) / `human` (未自動化) |
| `rubric` | PASS/FAIL を出せる具体基準。FAIL には file:line を要求 |
| `executor` | 実行主体。L0 行は抽象名、`bindings.<language>` で具体化 |
| `status` | `blocking` (既定) / `advisory` |
| `params` | 下位層で埋める穴の名前のリスト |
| `applies_to` | L3 行のみ: `library` / `cli` / `service` |
| `evidence` | 行が存在する根拠 (研究・実例・起票元 PR)。1 行 |
| `kind` | L4 行のみ: `invariant` (ドメインが強制) / `convention` (選んだ規約) |

## マージ規則

有効カタログ = `catalog.yaml` の l0 + l1 + (l3 のうち `applies_to` がプロジェクトの `archetypes` と交差する行) に、`bindings[language]` で executor を具体化し、プロジェクトファイルの `params` を充填、`overrides` を適用、`additions` を追加したもの。優先順位は **L4 > L3 > L2 > L1 > L0**。override は `reason` 必須 — 無ければ audit で violation。

## 操作

### init [project-root]
1. 対象リポジトリの CI 定義・ツール設定・スクリプトを読み、language と archetypes を判定する。
2. 有効カタログの各行を実在ゲートへマッピングし、`project-template.yaml` を元にプロジェクトファイルを書く: 埋められる `params` は埋める。
3. 報告する: (a) カタログにあるが repo に無い行 = ギャップ、(b) repo にあるがカタログに無いゲート = additions 候補または上位層への昇格候補。

### audit [project-root]
1. マージ済みカタログを作る。
2. `deterministic` 行: executor が CI/設定に実在し blocking かを突き合わせる。無い/advisory 化している → drift。
3. `check: human` の行を列挙する = 残ギャップ。
4. `params` 未充填、reason 無き override → violation。
5. 行 id ごとに `OK | drift | gap | violation` と根拠を表で返す。

### review <ref|diff>
1. マージ済みカタログから `check: agent` の行を集める。`deterministic` 行は CI が担うので再実行しない (CI 未整備の repo ではコマンドを直接実行する)。
2. **判定は実装と別コンテキストのフレッシュなサブエージェントで行う**。実装した本人 (同一コンテキスト) の自己判定は無効。
3. 出力契約: 行ごとに `id: PASS|FAIL|N/A — 根拠 (file:line)`。blocking 行に FAIL が 1 つでもあれば総合 FAIL とし、required_fixes を列挙する。

### promote <指摘>
1. `references/layers.md` の判定チェーンで層を決める。
2. L0〜L3 → `catalog.yaml` へ、L4 → プロジェクトファイルの `additions` へ行を追加する。`evidence` に起票元 (PR・指摘) を書く。
3. `deterministic` に落とせるか必ず検討する (lint ルール・guard ルール・check スクリプト)。落とせるならルール実装が本体で、行はそれを指す。行の `check` は実装された最も機械的な判定を指す。

### demote <行id>
誤検知の実績 (どの判定がなぜ誤りだったか) を `evidence` に追記した上で、`status: advisory` 化または `check` を一段人間側へ戻す。理由なき demote は禁止。

### export [path]
マージ済みカタログの `check: agent` 行を箇条書き Markdown に描画し、task-pipeline のレビュー観点ファイル (既定 `TASK_PIPELINE_REVIEW.md`、`review=` 指定があればそのパス) へ書く。`deterministic` 行は CI が担うので含めない。冒頭に「generated by review-catalog from <プロジェクトファイル> — 直接編集せず、元を編集して再 export」と書く。

### 引数なし
対象プロジェクトにプロジェクトファイルがあれば audit、無ければ init を実行する。

## 運用ルール

- **L4 行を別プロジェクトへコピーしない。** 共有したくなったらそれは L4 ではない — promote で上位層へ移す。`kind: invariant` の行は昇格もしない (ドメインが強制するものは他所では偽)。
- **同一指摘の 2 回目は promote する** (カタログ自身の行 `L0-twice-rule`)。
- 一般則を破る決定は decisions log に理由付きで記録する (`L0-override-logged`)。記録なき逸脱は汎用レビュアの恒久 FP 源になる。
- 新しい規約は「守れる最上位の層」に置く (`references/layers.md`)。

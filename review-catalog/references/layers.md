# 5 層モデル

境界の判定基準: **その行の「なぜ」を説明するのに、その repo の固有名詞 (クラス名・issue 番号・過去 PR) が要るなら L4。要らないなら上位層。**

| 層 | 定義 | 判定質問 | 根拠の出どころ | 置き場所 |
|---|---|---|---|---|
| **L0 普遍** | 言語・ドメインを問わず真 | 別言語の repo に持って行っても真か? | 研究・業界合意 | `catalog.yaml` の `l0` |
| **L1 個人/組織ポリシー** | 業界普遍ではないが、自分の全 repo に課したい選好 | 次のプロジェクトにも課すか? | 自分 (チーム) の決定 | `catalog.yaml` の `l1` |
| **L2 言語/エコシステム** | 言語仕様とツールチェーンが根拠 | 同じ言語の別 repo にコピーしてそのまま動くか? | 言語・ツールの仕様 | `catalog.yaml` の `bindings.<language>` |
| **L3 成果物アーキタイプ** | 配布ライブラリ / CLI / Web サービスという「形」が根拠 | 同じ種類の成果物なら必要か? | deliverable の性質 | `catalog.yaml` の `l3` (`applies_to` タグ) |
| **L4 プロジェクト固有** | この repo の歴史・ドメイン・選択に依存 | 上のどれでもない | repo 内の決定記録 | `<project>/docs/review-catalog.yaml` |

## 判定チェーン

上から順に問い、最初に yes になった層に置く:

1. 別言語でも真か → **L0**
2. 自分の全 repo に課したいか → **L1**
3. 同言語なら真か → **L2** (通常は新行でなく既存 L0 行への binding)
4. 同アーキタイプなら真か → **L3**
5. それ以外 → **L4**

迷ったら上位に置く。「守れる最上位の層」が正しい置き場所 — L4 に置いたままの規約は次の repo で再発明になる。

## L4 の二分

| kind | 意味 | 例 | 扱い |
|---|---|---|---|
| `invariant` | 問題ドメインが強制する。選択の余地がない | 「`fromAppDir()` は realpath しない (guard が fail open するため)」 | **コピーも昇格も禁止**。他所では偽 |
| `convention` | 選べたが選んだ規約 | テスト名は三人称現在の文 | L1 昇格候補。2 repo 目で使ったら promote |

## 優先順位と override

- 具体が一般に勝つ: **L4 > L3 > L2 > L1 > L0**。
- L4 が下位層を上書きする (例: 一般則「シンボリックリンクは解決せよ」を invariant が否定する) ときは、**override + reason + decisions log 記録が必須**。記録がないと、上位層しか知らない汎用レビュアが同じ誤指摘を恒久的に出し続ける。
- AI レビュアへの文脈ロードもこの層順 (L0 → L4)。FP の主因は L4 の未ロード。

## 観点とパラメータの分離

観点 (statement/rubric) は上位層、パラメータ (閾値・対象パターン・ルール表) は下位層に置く。例: 「構造不変条件は宣言ルールで執行される」は L0、どの不変条件か (`params.rules`) は L4。この分離が可搬性の実体 — 仕組みは L0〜L3 で説明でき、L4 に残るのは値と invariant と convention だけになる。

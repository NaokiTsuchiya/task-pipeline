# Fable への依頼プロンプト: リポジトリを見渡して次の候補を出す skill の構築

## 背景と目的

私は個人の skill 群を管理するリポジトリ (`NaokiTsuchiya/skills`) を持っていて、そこには `task-pipeline` と `task-prep` の 2 つの skill が入っています。

- `task-pipeline` — 承認済み issue を `/loop` で 1 件ずつ research → plan → implement → report の固定フェーズで自動消化する
- `task-prep` — 要望や既存 issue を、task-pipeline が消化できる検証可能な issue に変える。入力を省くと「棚卸し」に入り、**トラッカー上の既存 issue** を読み、受け入れ条件が甘い・裏取りされていない・依存が壊れているものを洗い出して次の一手を出す

まず現物を読んでください。以降の依頼はこれを前提にしています。

- `task-prep/SKILL.md` — 特に「棚卸し (入力なし)」節
- `task-pipeline/SKILL.md`
- `prompts/repo-survey-next-work.md` — 下記で説明する、今回置き換えたい現状のやり方そのもの
- `README.md`

### 今困っていること

task-pipeline は 1 タスクあたり 25〜40 分で PR まで到達するので、`ready` の在庫はすぐ尽きます。task-prep の棚卸しはそこでは役に立ちません。棚卸しが見ているのは**トラッカーに既に存在する issue** の欠陥であって、「まだ issue になっていない、コードベースを見れば見えてくるはずのやるべきこと」は範囲外だからです。つまり「open issue は全部きれいに書けている状態で、かつ ready が尽きた」ときに、次に何を issue にすべきかを決める手段が今の task-prep には無い。

いまはこれを `prompts/repo-survey-next-work.md` という、その場で Fable に渡す 1 枚の依頼文で埋めています。中身はコードベース全体・`docs/decisions.md`・open issue 全部・直近のマージ履歴を実際に読ませて、根拠付きの候補を最大 8 件、順位付きで出させ、**トラッカーには一切書き込ませない** (選ぶのは私) というものです。これは機能していますが、skill ではなく手元にコピペするプロンプトなので、

- 起動するたびに `<REPO>` を書き換えて手で渡す必要がある
- 前回出た候補・私が却下した候補を覚えていないので、同じ提案が再度出てくる可能性がある
- 候補から選んだあと、「私が要望文をもう一度手で書いて `/task-prep` に渡す」という、地味だが省けるはずの一手間が残っている

これを、task-prep 一式と同じ設計規律を持った **skill として作り直してほしい**。

## 作ってほしいもの

`prompts/repo-survey-next-work.md` がやっていること (コードベースの実査、decisions.md や open issue との突き合わせ、根拠付きの候補出し、順位付け、トラッカーへの書き込みはしない) を、繰り返し起動できる Claude Code skill にしてください。

- 出す候補の基準は `prompts/repo-survey-next-work.md` と同等で構いません: 何をするか、なぜ今か、裏取り (ファイルパス・行番号・コマンド実出力)、受け入れ条件の案、規模、依存。多くて 8 件、根拠が弱いなら少なくてよい。
- **トラッカーに書き込まない。** これは `prompts/repo-survey-next-work.md` で意図的に引いている線 (「何を作るか」を自動で決めさせない、選ぶのは私) で、そのまま引き継いでください。この線引きを変えるべきだと判断したなら、変える提案自体はしてよいですが、理由を添えて私に判断させてください。
- 私が候補から 1 件選んだあと、そのまま task-prep に渡せる状態で終わってほしい。渡し方 (要望文として整形して私に見せる、私が `/task-prep` にそのままコピペできる形にする、など) はあなたが決めてください。

## あなたに決めてほしいこと

### 1. 独立した skill にするか、task-prep の棚卸しを拡張するか (最重要)

task-prep の「棚卸し (入力なし)」と、今回作りたいものは、どちらも「次に何をすべきか分からないときの入口」という同じ役割で呼ばれます。一方はトラッカー越しに、一方はコードベース越しに、同じ問い (次に手を入れるべき場所はどこか) に答えています。

これを

(a) 完全に別の skill にする (`/repo-survey` のような新しい入口を作る)
(b) task-prep の棚卸しに合流させる (入力なしのときに、既存 issue の欠陥チェックに加えてコードベース探索もやる)
(c) その他あなたが考える形

のどれにするか、理由とともに決めてください。判断材料になりそうな点を書いておきます。

- 棚卸しは今のところ「トラッカーの生データを read-only サブエージェントに分担させ、メインコンテキストを汚さない」設計になっています (`task-prep/SKILL.md` の「棚卸し」節)。コードベース全体の実査はそれよりずっと重く、同じ 1 skill・1 対話に混ぜると、今の規模のガード (30 件超で全件は見ない、など) では足りないかもしれません。
- 分けると、「次どうする」を考えたい私は毎回どちらを呼べばいいか自分で判断しないといけなくなります。
- `prompts/repo-survey-next-work.md` は decisions.md・open issue 全部・直近マージ履歴も読んでいて、これは棚卸しが読んでいる範囲と大きく重なります (open issue の把握)。二重に調べるのは避けたい。

### 2. 起動頻度・トリガー

`prompts/repo-survey-next-work.md` は「ready が尽きたときに気づいた私が手動で渡す」運用でした。skill 化したときも同じ (私が明示的に呼ぶ) でいいのか、`ready` の残数を見て提案するような仕掛けまで持たせるのか。**後者を作り込むなら、「何を作るか」を勝手に決め始める方向に踏み出していないか**、線引きを意識して判断してください。

### 3. 前回却下した候補の扱い

同じ候補が毎回出てくると、私はそのたびに同じ判断をやり直すことになります。前回の実行結果 (出した候補、私が選んだもの・選ばなかったもの) をどこかに残して次回参照させるべきか、それとも棚卸しと同様に**都度フルスキャンでよい**と考えるか、あなたの判断で決めてください。どちらでも構いませんが、作り込むなら理由を、作り込まないならそれも理由を教えてください。

### 4. `docs/decisions.md` が無いリポジトリの扱い

`prompts/repo-survey-next-work.md` は「特に重要」として `docs/decisions.md` を読ませていますが、これは対象リポジトリに存在する前提で書かれています。無いリポジトリで動かしたときにどう振る舞うべきかは、あなたが決めてください (無視する、代替の情報源を探す、など)。**まだ存在しない使い方のための抽象化は作り込まないでください。**

## 制約

- 依頼の範囲を超えた機能追加・リファクタリング・抽象化はしないでください。起こり得ないケースのためのエラーハンドリングやフォールバックも不要です。
- **skill を書きすぎないでください。** 手順を全部列挙した指示書は、それを読む Claude の質をむしろ下げます。ゴールと境界と合否条件を書いて、判断は読み手のモデルに委ねる粒度にしてください。`task-prep/SKILL.md` がその意図で書かれているので、濃さの基準にしてください。
- `prompts/repo-survey-next-work.md` を skill 化したあとどう扱うか (残す・消す・棚卸しに畳み込む記述を足す) もあなたの判断で決めて、理由とともに報告してください。
- 情報が揃ったら動いてください。既に決まったことを再検討したり、取らない選択肢を私向けの文章で並べたりは不要です。選択肢を天秤にかけているなら、網羅ではなく推奨を出してください。
- 進捗を報告する前に、各主張をこのセッションの実際のツール結果に照らして確認してください。証拠を指させる仕事だけを報告し、未検証のものは未検証と明言してください。テストが落ちたなら出力とともにそう言い、飛ばした手順は飛ばしたと言い、終わって検証できたものは曖昧にせず終わったと言ってください。
- 私への応答は日本語でお願いします。最後のまとめは、途中の作業を見ていない読み手に向けて書いてください。結論を最初の 1 文に置き、作業中に自分で作った略語や記号の羅列は持ち込まないこと。
- コミットや push は、私が明示的に頼むまでしないでください。

## 進め方

1. まずこの依頼をスコープしてください。`task-prep` の棚卸し、`prompts/repo-survey-next-work.md` の実際の中身、Claude Code の skill 仕様は、推測ではなく手元で確認してから設計に入ってください。
2. 「あなたに決めてほしいこと」を、この時点でまとめて聞いてください。後出しの質問より、いま聞かれる方がありがたいです。
3. 独立した調査 (既存 skill の読み込み、コードベース実査の負荷見積もりなど) はサブエージェントに投げて、あなたは並行して作業を進めてください。サブエージェントが脱線したり文脈不足になっていたら介入してください。
4. 作りながら自分の仕事をチェックする方法を確立し、節目ごとにフレッシュなサブエージェントで仕様に対する検証を回してください。
5. 完成したら、**このリポジトリ自身 (`NaokiTsuchiya/skills`) を対象に実際に end-to-end で動かして**ください。実在するコードベースを実査させ、根拠付きの候補が実際に出るところまで確認してください。そのうち 1 件を task-prep に渡すところまでやってみて、引き継ぎがスムーズかを見てください。
6. 観測した挙動を報告してください。うまくいかなかった点は、うまくいった点と同じ密度で書いてください。

## 完成の判定基準

- このリポジトリ自身を対象に実行し、実コードの調査に基づいた根拠付きの候補が複数出た記録がある。
- トラッカーに一切書き込んでいないことが確認できている。
- 出てきた候補のうち 1 件を、実際に task-prep に渡すところまで一周した記録がある。
- 「あなたに決めてほしいこと」の各項目に、理由付きの回答がある。

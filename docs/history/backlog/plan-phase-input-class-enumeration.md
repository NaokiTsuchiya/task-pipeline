# plan フェーズの入力クラス導出を「diff からの機械的な列挙 → 分類」の手順に組み込む

## 背景

`docs/metrics/2026-08-05.md` の retro 分析で、`fail_reasons` の phase 別内訳のうち 23 件中 13 件 (57%) が
plan フェーズで発生し、うち 6 タスク (readme-list-sync / readme-feature-sync / state-cli-verbs /
sha-record-for-gate-light / gate-light-research-carryover / metrics-collect-scan-mode) の
`required_fixes` 本文がいずれも「境界条件・拒否側ケースの網羅漏れ」を指摘している。

当初「plan.md 提出前に verifier.md の FAIL 基準を自分の下書きに再照合する自己チェックを追加する」案を
検討したが、却下した。理由: 自己検証が有効に働くのは実行結果のような**外部の客観信号**があるとき
(implement フェーズの「テストが落ちていないか」の自己チェックはこれに当たる) であって、「入力クラス
を網羅できているか」は判断そのものである。同じ基準・同じ思考プロセスで自分の下書きを見返しても、
最初に見落とした盲点は再び見落としやすい — 新しい情報も独立した視点も入らないため。実際 SKILL.md
251 行目も「実行エージェントの self-check … は [検証エージェントの PASS の] 代替にならない」と明記
しており、後追いの自己照合は同じ設計上の弱点をゲート手前で再現するだけになる。

より効く方向は、**成果物を作る手順そのものを、判断より前に機械的な列挙を挟む構造に変える**ことである。
`task-pipeline/references/executor.md` の plan フェーズ節 (現行 65〜73 行目、「テスト網羅の最低ライン」
ブロックの「入力クラスの棚卸し」) は、現状「判定の仕様から入力クラスを導く」と書くのみで、その導出が
記憶・直感からの自由記述になっている。これを「まず diff 中の判定点 (条件分岐・バリデーション相当の
式) を機械的に (diff を読んで) 洗い出し、そのあとで各判定点にクラスを割り当てる」という 2 段階の
手順に変えれば、列挙の起点が「自分の記憶」ではなく「実際の diff」という外部の根拠になり、洗い出し
自体の網羅性が上がる。

## 要求

`task-pipeline/references/executor.md` の plan フェーズ節「テスト網羅の最低ライン」ブロックの
「入力クラスの棚卸し」を、以下を満たす形に書き換える:

1. 現行の「その判定が受け取りうる入力を形状のクラスに分け…」という導出を、次の 2 段階の手順に組み
   替える:
   - **段階 A (列挙)**: 変更が触れる判定点 (条件分岐・比較・正規表現マッチ・型チェック・範囲チェック
     等、帰結を左右するあらゆる判定相当の式) を、diff を実際に読んで機械的に洗い出す。記憶や直感で
     「ありそうな境界」を先に思い浮かべるのではなく、diff にある判定式を起点にする。
   - **段階 B (分類)**: 段階 A で洗い出した判定点それぞれについて、その判定の仕様 (何を根拠に帰結を
     決めるか) から入力クラス (受理側・拒否側両方) を導き、代表ケースを割り当てる。現行の分類ロジック
     (相対パスの拒否なら `.`/`app`/`./app` は別クラス、数値範囲なら負数/0/上限ちょうど/上限超え、等)
     はそのまま維持する。
2. **段階 A が段階 B に先行すること、および段階 A が diff を根拠にすることを明文化する** (「見直す」
   「再照合する」のような後追いレビューの言葉遣いにしない — これは前回却下した自己チェック案との違い
   を保つため)。
3. 「エントリポイントごとの確認」「除外の明示」の 2 サブ項目は現行の記述を変えない (段階 A・B は
   「入力クラスの棚卸し」サブ項目の内部の手順変更にとどめる)。
4. 変更対象は `task-pipeline/references/executor.md` の 1 ファイルに限定する。`verifier.md` /
   `SKILL.md` は変更しない — verifier.md の FAIL 基準 (どのクラスが揃っているべきか) はそのまま
   有効で、この issue は executor がその基準を満たす確率を上げる「作り方」だけを変える。

## 検証可能な受け入れ条件

1. `git diff --name-only <実装前 HEAD> HEAD` が `task-pipeline/references/executor.md` の 1 ファイル
   のみを含み、`verifier.md` / `SKILL.md` を含まないこと。
2. 「入力クラスの棚卸し」サブ項目 (またはその直下) に、判定点の列挙が診断・思考より先に行われ、かつ
   その列挙が diff (実際の変更差分) を根拠にすることを明示する文言が追加されていること (例: 「diff
   を読んで」「変更差分から」に相当する、列挙の起点が diff であることを示す語彙が含まれる)。
3. 追加された文言の中で、列挙 (段階 A) の記述が分類 (段階 B) の記述より前に置かれていること (文章の
   順序として、まず洗い出し、次に分類、という構成になっている)。
4. 追加された文言が「自分の下書きを見直す」「再照合する」「レビューする」のような後追い確認の言い回し
   を主体とした表現になっていないこと (前段の却下理由と矛盾する設計に戻っていないことの確認)。
5. 「エントリポイントごとの確認」「除外の明示」の 2 サブ項目の文面が、この変更の前後で意味的に変わっ
   ていないこと (diff 上、この 2 項目の行に変更が無いか、あっても言い換えのみで要求内容が同じである
   こと)。
6. `sh tests/run.sh` が引き続き全スイート `failed:0` で通る (このタスクはテストコードを変更しないた
   め新規テストの追加は不要だが、既存スイートを壊していないことを実行して確認する)。

## 備考

これは task-pipeline 自身の運用改善であり、verifier.md の判定基準そのものを変えるものではない
(verifier.md 側の基準はそのまま)。当初案 (提出前の自己チェック) を却下した経緯は上記「背景」に残す。

# 枯渇・ペーシングの到達不能な指示 3 点を直す

## 背景 / 現状

行番号はコミット 3015e87 時点の task-pipeline/SKILL.md。3 点とも「規定はあるが、そこへ到達する経路が無い」型の欠陥で、(a) は本セッションの敵対的検証で確定している (CONFIRMED)。

**(a) max_open 到達中は停止経路に到達できない。** レビュー待ち上限のチェック (151 行) は毎イテレーション手順 1 の中で承認 (アダプタ `list` 呼び出し) より前に発火し、「1 行報告し、dynamic なら ScheduleWakeup 1800 秒を予約して終える」。一方、ループ停止の全経路は「承認で `list` が `{"tasks": []}` を返したら」(465 行) から始まり、追従打ち切り (473 行「丸 1 日どの PR も動いていない」) はその内部にあり、`watch.idle` の加算も「候補が枯渇した後だけ」(94 行・368 行・473 行の 3 箇所すべてに明示) に限定される。よって approve=auto + finish=pr で max_open 本の PR が放置されたまま誰もマージしないと、30 分おきの空 wakeup が停止も最終報告も無く無期限に続く。毎イテレーション冒頭のマージ回収は「証明できたタスクだけ」を done にするので、マージが無い限り出口にならない (検証済み)。

**(b) 枯渇報告の内訳を作る手段が未定義。** 枯渇時フロー (468-469 行) は「トラッカーから候補になっていない issue を状態別に数え」「候補になっていない issue が 30 件までのとき本文まで読む」ことを要求するが、アダプタ契約 (references/adapter-protocol.md) の操作は `list` (候補のみ返す) と `mark` の 2 つだけで、起動プロンプトも「この形のみ」(214 行) に固定されている。非候補 issue を列挙・読解する操作はどこにも定義されておらず、コンテキスト規律 (54 行) はオーケストレーター自身のトラッカー直読みを禁じている。隣の依存昇格 (440 行) が委任先ファイルパスまで明文化しているのと対照的に、内訳には実行主体も手段も無い。

**(c) cron 配下では追従打ち切りが到達不能。** `watch.idle` は watch プロセスの timeout 終了通知でのみ +1 されるが (473 行「保険の wakeup では増やさない」)、固定間隔 cron 配下では watch プロセスがターンを跨げず (365 行)、timeout 通知は構造的に届かない。枯渇後の追従で cron は CronDelete されない (472 行) ため、放置 PR が 1 本あると打ち切り条件が永遠に満たされず、毎イテレーション catch-up 観測のコストを払いながら cron ジョブが回り続ける。365 行の劣化モード注記はコスト劣化のみで、打ち切りが効かないことに触れていない。

## 要求

task-pipeline/SKILL.md の修正で 3 点を閉じる。(b) でアダプタ契約に操作を足すか、既存の委任パターンで解くかは実装で選んでよい。

1. (a): max_open 到達中でも、枯渇判定相当と追従打ち切りに到達できるようにする (例: 上限到達イテレーションでも `list` は呼んで枯渇を判定する、または上限到達中も timeout 通知で `watch.idle` を数えると明記する)。
2. (b): 内訳を作る実行主体と手段を明文化する。候補: アダプタに read-only の第 3 操作を足す (adapter-protocol.md と references/adapters/gh.md・markdown.md の 3 ファイルすべての更新が要る)、または task-prep のトラッカー定義パスを渡す read-only サブエージェントの起動プロンプトを SKILL.md に固定する (依存昇格 440 行と同型)。どちらでも、コンテキスト規律 (メインでトラッカー生データを読まない) と矛盾しないこと。
3. (c): cron 配下の打ち切り条件を規定する (例: catch-up 観測が連続 N 回無変化なら idle 相当を加算) か、365 行の劣化モード注記に「idle による自動打ち切りは効かない」旨を明記する。どちらを選んだかが読み手に分かること。

## 受け入れ条件

1. 「max_open 到達 + 全 PR に 6 時間 × 4 回の無変化」の机上トレースで、変更後の SKILL.md の指示だけから「追従を終えてループを止める」と最終報告に到達できる。
2. 枯渇時の内訳について、実行主体 (誰が) と手段 (どの操作 / どの委任先で) が SKILL.md に明文であり、その手段がコンテキスト規律の節と矛盾しない。アダプタ操作を足した場合は adapter-protocol.md と references/adapters/gh.md・markdown.md の全部が同じ操作を定義している。
3. cron 配下の枯渇後追従について、打ち切り条件の規定または「自動打ち切りは効かない」の明記のどちらかが、cron の劣化モードを扱う節にある。

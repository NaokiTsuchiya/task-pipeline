# approve=auto のスタブ検査を着手マーク後に移す

## 背景 / 現状

行番号はすべてコミット 3015e87 時点。先行タスクのマージでずれている場合は、引用文言を grep して現在の位置を特定すること。

- task-pipeline/SKILL.md の承認手順 3 の `auto` 分岐 (209 行) は「そのタスクの `tasks/<id>.md` がスタブのまま (本文が取得できていない) なら着手しない。id を報告して次の候補に移る」を規定する。この検査は承認時点、つまり `mark <id> in_progress` (タスク実行手順 1) より前に行われる。
- gh アダプタ (task-pipeline/references/adapters/gh.md) は設計として、`list` では全候補をスタブとして書き (71 行「この時点では本文もコメントも書かない」)、本文の書き出しは `mark in_progress` のときだけ行う (110 行「タスク本文の書き出し (`in_progress` のときだけ)」)。この遅延は同ファイル 146-150 行に理由付きで記録された意図的設計である。
- したがって gh トラッカーでは、承認時点の候補は常に全件がスタブであり、`approve=auto` は順位 1 位から全候補を「着手しない」で飛ばす。SKILL.md 自身が例示する構成「`gh ?label=ready finish=pr approve=auto`」(26 行) が 1 件も実行しないまま空回りする。全候補を飛ばした後の挙動も未定義 (枯渇時フローは「`list` が `{"tasks": []}` を返したときだけ」と 465 行に明記されており、該当しない)。
- SKILL.md 自身が gate 判定について「gh アダプタはタスクファイルを `mark in_progress` の時点で書き直すので、この判定を `mark` より前に行ってはならない」(244 行) と同じ罠を認識済みで、auto のスタブ検査だけが mark 前に置かれている。
- markdown アダプタは `list` 時点で全文を書くため、この検査は markdown では常に空振りする。つまり現行の検査位置では、ガード本来の対象 (mark 失敗で本文が取れないままのタスク) を弾く時点がどちらのトラッカーにも存在しない。
- コンテキスト規律 (SKILL.md 50-56 行) はオーケストレーターがタスク本文を Read することを禁じており、スタブ判定には gate 判定 (239 行の sed + grep) と同様の機械的手段が要るが、現行の 209 行には判定手段の指定が無い。

以上は本セッションで独立サブエージェントの反証試行を通して確定済み (CONFIRMED)。

## 要求

task-pipeline/SKILL.md を次のように直す。アダプタ側 (references/adapters/) は変更しない。

1. auto のスタブ検査を、承認手順 3 から外し、タスク実行手順 1 の `mark <id> in_progress` の後 (gh アダプタが本文を書き出した後) に移す。ask / auto 共通の位置にするか auto のときだけ判定するかは実装で決めてよいが、検査の目的 (本文の無いタスクを自動実装に流さない) が auto で機能することを保証する。
2. スタブ判定を機械的手段で規定する (本文を Read しない)。例: gh アダプタのスタブが必ず含む案内行 (adapters/gh.md 81-83 行のスタブ書式) の grep。判定手段が何をアンカーにするかは、アダプタ契約 (references/adapter-protocol.md のスタブに関する記述) と突き合わせて決めること。
3. 検査がタスクを弾いたときの挙動を定義する: そのタスクの処置 (queue から外す / blocked にする 等)、次の候補への遷移、全候補が弾かれた場合のイテレーションの終え方。同じ候補を毎イテレーション弾き続ける無限の空回りにならないこと。

## 受け入れ条件

1. gh トラッカー相当 (list はスタブのみ書き、mark in_progress で本文を書く) の候補 2 件を仮定した机上トレースで、`approve=auto` の順位 1 位が `mark in_progress` → 実行エージェント起動まで到達することを、変更後の SKILL.md の文面だけから追える。
2. mark in_progress の後も本文が書けずスタブのまま残ったタスク (mark 失敗経路) だけが着手拒否され、その後の挙動 (タスクの処置、次候補への遷移、全候補該当時の終わり方) が SKILL.md に明文で定義されている。
3. スタブ判定が機械的 (grep 等のコマンド) に規定され、オーケストレーターがタスク本文を Read する指示になっていない。
4. 変更後の SKILL.md に、承認時点 (mark 前) でスタブ検査を行う記述が残っていない。

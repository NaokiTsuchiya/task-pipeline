# markdown backlog アダプタ

`source` はバックログの **リストファイル** (例: `./backlog/TASKS.md`)。相対パスは **state dir の親ディレクトリ** (プロジェクトルート) を基準に解決する — 起動プロンプトは対象プロジェクトのパスを渡してこないので、カレントディレクトリに依存させないこと (gh アダプタと同じ規則)。タスク本文は **1 タスク 1 ファイル** で、リストファイルと同じディレクトリに置く。**ファイル名 (拡張子 `.md` を除く) がタスクの id** で、リスト側の行はその id を参照する。

## フォーマット

リストファイル (`backlog/TASKS.md`):

```markdown
# バックログ

- [ ] add-slugify
- [ ] fix-login-timeout (blocked: 認証サーバの仕様確認待ち)

## In Review

- [ ] improve-logging (PR: https://github.com/owner/repo/pull/12)

## Done

- [x] setup-ci
```

アイテムファイル (`backlog/add-slugify.md`。ファイル名 = id):

```markdown
# textutils に slugify 関数を追加する

本文。要求や受け入れ条件のメモなど自由に書く。
インデントの有無にかかわらず、アイテムファイル内のチェックリストがタスクとして拾われることはない。
```

規則:

- リストの並び順 = 実行順。
- タスクとして拾うのは、`## In Review` / `## Done` セクションより前 (バックログ本体) にある **行頭の `- [ ] <id>` 行だけ**。`(blocked: ...)` または `(wip)` が付いた行は除外する。それ以外の行 (見出し・文章・インデントされた行) はすべて無視する。
- 状態の意味: バックログ本体 = 未着手、`(wip)` = パイプラインが着手中 (復帰は suffix を手で消す)、`(blocked: ...)` = 進められない。**`mark blocked` は対象行を必ずバックログ本体に置く** (下記 `mark` 参照。`## In Review` にあった行も blocked にする際にバックログ本体へ戻される) ので、`(blocked: ...)` は常にバックログ本体にある — suffix を手で消せば候補に復帰する。`## In Review` = パイプラインの作業完了・レビュー/マージ待ち、`## Done` = マージ/受け入れ完了。
- **In Review から Done へ移るのは、ユーザーがマージ/受け入れしたとき**。行を手で移すほか、`finish=pr` ならパイプラインがマージを git 履歴で検知して自動で回収する (`mark done`)。**blocked にせず**単に差し戻したいときは、In Review の行をバックログ本体に戻せば list に再登場して候補に復帰する (パイプライン側の反映遅延ガードにより、復帰は 2 回目の list からになる)。
- **`## In Review` セクション内に `(blocked: ...)` が付いた行を見つけた場合の復帰**（`mark blocked` は常にバックログ本体へ戻すので通常は起こらないが、手作業や本仕様変更前の名残りで残っていることがある）: suffix を消すだけでは戻らない (`## In Review` は `list` の走査範囲外のため、上記 :36)。まず行をバックログ本体の末尾へ移し、そのうえで `(blocked: ...)` suffix を消す。**行が最初からバックログ本体にある通常のケースでは、suffix を消すだけでよい。**
- タイトルはアイテムファイル先頭の `# ` 見出し。無ければ最初の非空行、それも無ければ id。
- id はファイル名なので、アイテムファイルのタイトルや本文は自由に書き換えてよい (同一タスクのまま)。
- リストに載っていないアイテムファイルは無視される (下書き置き場にできる)。

## `list`

1. source を読み、上記の規則で id を上から順に列挙する。同じ id の行がファイル内に複数あれば `{"error": "id が重複しています: <id>"}` を返す。
2. 各 id について `<source と同じディレクトリ>/<id>.md` を読む (id ごとに独立なので並列に読んでよい)。存在しなければ `{"error": "アイテムファイルがありません: <id>.md"}` を返す。
3. 各タスクについて `<state dir>/tasks/<id>.md` を書く:

   ```markdown
   ---
   id: <id>
   title: "<タイトル>"
   source: <リストファイルのパス>
   gate: light
   ---
   <アイテムファイルの内容 (タイトル見出しを除く)>
   ```

   `title` は**ダブルクォートで囲む**。見出しの `:` や `#` で YAML が壊れないようにするため (`# fix: login timeout` のような見出しは普通にある)。タイトル中の `"` は `\"`、`\` は `\\` にする。それ以外は書き換えず、日本語などの非 ASCII 文字はそのまま書く。

   **`gate: light` の行は、アイテムファイルに `<!-- task-pipeline:gate=light -->` の行がある (行全体一致) ときだけ入れる** (無ければ行ごと省く。`gate: full` とは書かない)。これが gate 宣言のタスクファイル側の表現で、オーケストレーターの gate 判定 (SKILL.md「タスク実行」手順 1) が見るのはこの 1 行だけである。

   **アイテムファイルの内容は逐語で書く。1 文字も加減しない。** 要約・整形・空行の詰め・末尾行の省略をしない。マーカー行や HTML コメントもそのまま残す (frontmatter に転写した後も本文から消さない)。この転記は要求と受け入れ条件を executor / verifier へ渡す唯一の経路である。

4. 応答: `{"tasks": [{"id": "...", "title": "...", "updated_at": "<アイテムファイルの mtime、ISO8601 UTC>"}]}` のみ。
   - **`priority` は返さない** — このトラッカーではリストの並び順がそのまま実行順の表明なので、優先度を別の軸で二重に持たない (オーケストレーターは `priority` の無いタスクをすべて同じ中位として扱う)。`labels` / `milestone` も無いので返さない。
   - `updated_at` はアイテムファイルの mtime (`date -u -r <path> +%Y-%m-%dT%H:%M:%SZ`)。オーケストレーターの順位キャッシュがこれを見るので、**本文を編集したら順位が付け直される**。取れなければキーごと省く (その場合は id 集合が変わるまで並びが固定される)。
- source が読めないなど取得できない事情は `{"error": "..."}` で返す (空の一覧を返さない)。

## `mark <id> <status> [reason|ref]`

1. source 内で id により該当行を特定する (`- [ ] <id>` または `- [x] <id>` で始まる行。suffix の有無は問わない)。見つからなければ `{"ok": false, "error": "..."}`。
2. 該当行だけを操作する。他の行に触らない。
   - `in_review`: 行を元の位置から削除し、`- [ ] <id>` を `## In Review` セクションの末尾に追加する。ref があれば ` (PR: <url>)` または ` (commit: <hash>)` を付記する。`## In Review` セクションが無ければ作る (`## Done` があればその直前、無ければファイル末尾)。
   - `done`: 行を元の位置から削除し、`- [x] <id>` を `## Done` セクションの末尾に追加する (セクションが無ければファイル末尾に作る)。
   - `blocked`: **行が `## In Review` セクション内にあるときは、先に行をその位置から削除し、バックログ本体の末尾へ移す** (`in_review` と逆方向の移動。行に付いている ` (PR: <url>)` / ` (commit: <hash>)` の ref suffix はそのまま残す)。行がバックログ本体にあるとき (元からそうだった場合、または今移したばかりの場合) は、` (wip)` が付いていれば外し、行末に ` (blocked: <reason>)` を追記する。**結果として `(blocked: ...)` が付いた行は常にバックログ本体にある。**
   - `in_progress`: **既に ` (wip)` が付いていれば着手させない**: `{"ok": false, "error": "already in progress — 別のセッションが着手済み"}` を返す。付いていなければ行末に ` (wip)` を追記する (行は元の位置のまま)。加えて、アイテムファイルから `<state dir>/tasks/<id>.md` を `list` と同じ形式で書き直す (承認から実行までにアイテムファイルが編集されていても、実行開始時点の内容を正とするため — gh アダプタと同じ鮮度規則)。書き直しに失敗しても ` (wip)` の追記が成功していれば `{"ok": true}` を返す。**応答には `gate_declared: true|false` を含める** — アイテムファイルにマーカー行があったかどうかをそのまま返す (オーケストレーターが自分の gate 判定と突き合わせるため。gh アダプタと同じ)。
3. 応答: `{"ok": true}` または `{"ok": false, "error": "..."}` のみ。

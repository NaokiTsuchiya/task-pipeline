判別ビットを導入したら set/clear の全ライフサイクルを書き切るまで確定しない。さらに言えば、判別子が要ること自体が「座標を破壊する遷移がある」ことの徴候である。

# 判別ビットはライフサイクル全体を宣言してから確定する — そして判別子の必要自体を疑う

状態モデル v2 の設計で、`rebase_fix` の 2 入口・2 出口を 1 ビット
(`asks.rebase.taken`) で判別する形を導入した。敵対検証が 2 段階で穴を示した。

**第 1 段: 消し忘れのラッチ残留。** 初版は「誰が立てるか」だけを宣言し、失敗出口
(give-up) が taken を消さないため、次の要求→開始が前提 (taken 偽) を永久に満たせなく
なる列が構成された — v1 の欠陥 10 (出口が永久に塞がる) と同型の穴を、それを塞ぐための
機構自身が再生産していた。フラグを 1 つ足すたびに、set/clear を行う verb の完全な
集合を遷移表の効果欄に列挙し、「set されたまま到達する休止ノードが無いか」を到達
可能性の目で見ること。また、複数フィールドの組から座標を作るときは生の積ではなく
優先順位つきの導出関数で全域に定義し、分割であることを関数形で保証すること。

**第 2 段: 判別子は座標破壊の代償だった。** ビットで入口を判別する必要があったのは、
finalize 割り込みが `run.kind` (engagement の来歴 = v2 の中心座標) を破壊的に上書き
していたからである。検証はこの上書きが来歴由来の導出 (mark) と gate の不変条件を
壊すことも示した。最終形は割り込みを「kind の切り替え」ではなく「同じ run 内の
フェーズ迂回 (finalize ⇄ rebase_fix)」にし、kind を保存した — すると入口・出口の
判別は kind そのもので済み、判別ビットの役割は消費マーカーに縮んだ。

教訓の順序が大事である: **判別子を足したくなったら、先に「どの遷移がどの座標を
破壊しているせいで判別が必要になったのか」を探す**。破壊をやめられるなら、判別子は
そもそも要らない。

# 活動は保存せず、意図とリースから導出する — この方針は正しかった

v1 の `watch.state == "watching"` は「追従している」という**活動の主張**だった。
活動は揮発資源 (watch プロセス) の実在と同期していなければ嘘になるが、同期を
保証する仕組みは無く、確認済み欠陥 12 件のうち 3 件 (block / recover-done /
restore が watching を残す) がこの嘘の形をしていた。堅牢化 (PR #28) は遷移の
たびに静止処理 (`withStoppedWatch`) を差し込むことで塞いだが、これは「嘘を
書ける表現のまま、書き手全員に訂正を義務付ける」対処である。

v2 設計では表現そのものを変えた: 保存するのは**耐久的な意図** (`attention`:
機械に委ねるか人に委ねるか + 理由) と**リース** (`probe.proc` + 所有セッション)
だけで、「いま追従すべきか」は `resting ∧ open ∧ attention=auto ∧ asks 静穏`
からの導出にした。嘘を書くフィールドが無いので、静止処理も、その呼び忘れも、
概念ごと消えた。

裏付け: フレッシュな文脈の敵対検証者に「この設計で欠陥 12 件 + 回帰 1 件と
同じ実害を起こすイベント列を構成せよ」と課したところ、13 件全件が防衛に成功した
(HOLDS 13/13。破れたのは新設機構の縁で、別教訓に記録)。**状態設計で「X 中である」
というフィールドを足したくなったら、それが活動の主張 (実在との同期が要る) か、
意図の記録 (単独で真になれる) かを先に問う** — 保存してよいのは後者だけで、
前者は導出式に置き換える。

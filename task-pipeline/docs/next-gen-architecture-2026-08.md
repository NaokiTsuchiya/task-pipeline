# 次世代タスクパイプライン (v3) アーキテクチャ設計書 (2026-08)

本ドキュメントは、Paseo デスクトップ環境および Oh My Pi (omp) 実行基盤のネイティブ機能を最大限に活かし、従来の長命 LLM オーケストレーターの制約をゼロベースで解消した**次世代タスクパイプライン (v3)** の完全な設計仕様書である。

---

## 1. 背景と実測に基づく設計原則

### 1.1 従来アーキテクチャの構造的ボトルネック
`task-pipeline` の実測データ (`cost-analysis-2026-07.md`、2026-08 運用ログ) より、以下の制約が確定している:

| # | 観測された事実 | 影響 |
|---|---|---|
| **F1** | オーケストレーター (LLM セッション) 費がタスク総コストの **24〜32%** を占める | 会話履歴の肥大化に伴い、毎ターンのプロンプト再送コストが増大。 |
| **F2** | オーケストレーターの処理の大半は `state.ts next` の決定論的ディスパッチ | 知能を要さない機械的処理に高価な LLM トークンを消費している。 |
| **F3** | 長命 executor は再開ごとに再キャッシュ税が発生 (93k→406k トークン) | フェーズ累積でコンテキストが単調増加し、費用対効果が悪化。 |
| **F4** | ステップ間の待機遅延 (最大 1800 秒) | ポーリング待ちにより、1タスクあたり 75〜150 分の無駄な待機が発生。 |
| **F5** | 機械検証可能なタスクでの検証ゲート 100% オーバーヘッド | 仕様が固いタスクでも一律に LLM 検証ゲートを通すため無駄が生じる。 |

### 1.2 コア設計思想 (The 5 Pillars)
1. **永続状態と会話コンテキストの完全分離 (Stateless Control)**: 会話履歴やセッションメモリに状態を持たせず、ディスク（台帳）を唯一の正 (Single Source of Truth) とする。
2. **非LLM常駐ドライバー (Zero-Token Driver)**: 機械的ディスパッチとイベントポンプを非LLMの軽量プロセス (Deno/TypeScript) で常駐させ、オーケストレーター費用を完全ゼロ ($0) にする。
3. **Task Cell による完全隔離**: 1タスクごとに独立した Paseo Workspace ＋ Git worktree を作成し、作業ディレクトリ・プロセス・ブランチの干渉を構造的に遮断する。
4. **イベント駆動 0 秒ハンドオフ**: `paseo wait` long-poll およびプロセス終了通知により、サブエージェント完了から次ステップへの遷移遅延をゼロにする。
5. **リスク適応型動的 DAG (Dynamic Risk Tiering)**: タスクの難度・リスクに応じて、フェーズ構成・モデル種別・検証強度（Shell-Check vs 異種モデル合議）を動的生成する。

```
┌─────────────────────────────────────────────────────────────────────────────┐
│ 【L4: 人間プレーン (Human Plane)】                                          │
│   ・GitHub Issues / PR レビュー / マージ / PushNotification                 │
└──────────────────────────────────────┬──────────────────────────────────────┘
                                       │ 承認 / レビュー
┌──────────────────────────────────────▼──────────────────────────────────────┐
│ 【L2: 判断プレーン (Ephemeral Judgment)】 [トークン従量 / 単発使い捨て]     │
│   ・Triage / トリアージ (課題の優先順位付け)                                 │
│   ・Verifier / 検証ゲート (独立した異種モデル合議)                           │
│   ・Exception Handler / 例外対応 (blocked やコンフリクト発生時のみ起動)      │

                                       │ 要求 / 判定結果
┌──────────────────────────────────────▼──────────────────────────────────────┐
│ 【L1: 制御プレーン (Thin Task Controller / Driver)】 [トークン消費: ゼロ]   │

│   ・異常復旧用デッドマンスイッチ (`create_schedule`)                         │
└──────────────────────────────────────┬──────────────────────────────────────┘

│   ・ディスク上の台帳こそが唯一の正                                          │
└─────────────────────────────────────────────────────────────────────────────┘
                                       │ 1タスク = 1セルとして完全隔離
┌──────────────────────────────────────▼──────────────────────────────────────┐

│   ┌───────────────────────────────────────────────────────────────────────┐ │

│   │   ・専用 Paseo Workspace ＋ Git worktree / ブランチ                   │ │
│   │   ・Executor (実装エージェント): タスク難度に応じた動的ライフサイクル  │ │
│   │   ・Runtime Scripts / 成果物マニフェスト (`runs/<id>/`)               │ │
│   └───────────────────────────────────────────────────────────────────────┘ │
```

## 3. レイヤ別詳細仕様

### 3.1 L0: 永続台帳 (Durable Ledger)
- **責務**: 全パイプライン実行の現在状態・履歴・成果物ポインタの永続化。
- **データ構造**:
  - `state.json`: タスクキュー (`queue`)、完了控え (`completed`)、実行中状態 (`run`)。
  - `runs/<id>/`: 成果物マニフェスト (`research.md`, `plan.md`, `verdicts/`, `paseo-workspace.json`)。
- **排他制御**: 全書き込みは楽観ロック (`--expect-executor`, `--expect-session`, CAS) で保護。競合時は再読み込みして安全にリトライ。

### 3.2 L1: 制御プレーン (Driver / Thin Controller)
- **実体**: `omp hub(op: "start", name: "task-pipeline-driver")` で常駐する Deno スクリプト (`scripts/pipeline-driver.ts`)。
- **イベントポンプ**:
  - 飛行中の各エージェントに対して `paseo wait <agentId> --timeout 1800 --json` で long-poll。
  - サブエージェントが `idle` になった瞬間 (0秒) に復帰し、protocol 行の鮮度規則（`idle` ∧ `UpdatedAt` > 前回時刻 ∧ 現在フェーズ一致）を検証。
  - `touch-executor` を呼び、即座に次のアクション（検証ゲートまたは次フェーズ）を実行。
- **デッドマンスイッチ**:
  - Driver プロセス自身の死活監視として `create_schedule`（15分間隔）を配置。Driver の heartbeat が途切れた場合のみフレッシュエージェントが起床して Driver を再起動。

### 3.3 L2: 判断プレーン (Ephemeral Judgment)
- **実体**: 必要な瞬間だけ `paseo run --output-schema` または omp `task` で単発起動されるエフェメラル LLM。
- **構成**:
  - **Triage**: 候補一覧と優先度ルールを読み、1位の選定理由と順位リストを JSON で返して即終了。
  - **Verifier**: 実装者のコンテキストを遮断し、独立した指示ファイル (`verifier.md`) と成果物・テスト結果のみを照合して verdict JSON を返して即終了。
  - **Exception Handler**: `blocked` や予期せぬスキーマ破損時のみ人間介入プロンプトまたは PushNotification を発行。

### 3.4 L3: 作業プレーン (Task Cells - Paseo Workspace)
- **Task Cell の境界**:
  - タスク 1 件につき 1 つの Paseo Workspace (`wks_...`) と専用 Git worktree を作成。
  - 作業ツリー、ビルドプロセス、ブラウザ状態、環境変数が他タスクから完全に隔離される。
  - タスク完了時（マージまたは withdraw 時）に Workspace を自動アーカイブ。

## 4. リスク適応型動的 DAG (Dynamic Risk Tiering)

タスク開始時、`task-prep` の裏取りで確定した `risk` 宣言および `gate` 宣言に基づき、実行 DAG を動的にコンパイルする。

```
compile(class, gate, finish) → runs/<id>/plan.json
```

| タスク分類 (Class) | 判定基準 (6項目該当) | ワークフロー (Gate) | Executor 寿命 | 検証ゲート (Verifier) | 想定コスト / 時間 |
|---|---|---|---|---|---|
| **Trivial (低リスク)** | 6項目すべて非該当、かつ機械的検証可能 (純ドキュメント、軽微な命名統一、テスト整理) | `gate: light`<br>(3フェーズ) | ワンショット<br>(1体で完結) | **Shell-Check ゲート**<br>(テストコマンド等の機械的終了コードのみで PASS/FAIL 判定。LLM 呼び出しゼロ) | コスト: **極小 (~135k tokens)**<br>時間: **~2分** |
| **Standard (通常)** | 単一モジュールの通常の機能追加・不具合修正 | `gate: full`<br>(4フェーズ) | 長命 executor<br>(フェーズ間再開) | **独立 LLM Verifier (1体)**<br>(FAIL 時の再開 ≤ 3回) | コスト: **標準 (~700k tokens)**<br>時間: **~30〜45分** |
| **High (高リスク)** | 公開API変更、スキーマ移行、セキュリティ、並行性、血流域モジュール、新規依存のいずれか | `gate: full`<br>(4フェーズ) | フェーズ毎フレッシュ<br>(前フェーズの思い込み遮断) | **異種モデル合議 Verifier**<br>(異なる 2 プロバイダによる両 PASS 必須) | コスト: **高 (堅牢性最優先)**<br>時間: **~60〜90分** |

### 検証不変条件 (Audit Floor)
- **検証強度は「上げる方向」にしか動かせない**: `providers_by_class` によるモデル切り下げは executor（実装側）のみ許可し、verifier（検証側）は `high` への昇格のみ許可する。
- **Shell-Check への置換**: Trivial タスクにおける Shell-Check は「LLM の曖昧な意見より強力な機械的証明」への置換であり、検証の弱体化ではない。機械判定できない条項が 1 つでも残るタスクは Standard (LLM Verifier) へ自動昇格する。

## 5. 段階的実装ロードマップと分解タスク

本アーキテクチャへの移行を 3 つのフェーズに分解し、各フェーズが独立して機能・ロールバック可能な設計とする。

### 【Phase 1: 即時改善と可観測性・即時起床の確立】(進行中)
- [x] **Issue #129**: Paseo 経路のサブエージェント実行中におけるメインセッション進捗表示 (Progress Banner) の導入
- [x] **Issue #130**: バックグラウンド Watcher プロセス (`scripts/watch-agent.sh`) による Paseo executor 停止の 0 秒起床
- **効果**: 現行パイプラインのまま待機遅延 (75〜150分) を解消し、メイン画面でのブラックボックス状態を排除。

### 【Phase 2: 常駐 Driver (制御プレーン) による非LLMディスパッチ】
- [ ] **Task 2-1: Deno 常駐 Driver (`scripts/pipeline-driver.ts`) の実装**
  - `state.ts next` を呼び出し、固定文面アクション (`run`, `send`, `touch-executor`, `verdict-path`) を実行するイベントループの実装。
- [ ] **Task 2-2: `omp hub(op: "start")` 連携とシャドー運転**
  - Driver を観測モードで常駐させ、既存 LLM オーケストレーターと判定の一致を検証。
- [ ] **Task 2-3: ディスパッチの完全移管とデッドマンスイッチ配備**
  - 機械的ディスパッチを Driver に完全移管。LLM はトリアージ・承認・例外対応の単発起動に特化。`create_schedule` による Watchdog を配備。
- **効果**: オーケストレーターのコンテキスト肥大化と費用 (24〜32%) を完全に $0 化。

### 【Phase 3: Task Cell カプセル化と動的 DAG (Risk Tiering)】
- [ ] **Task 3-1: Paseo Workspace による Task Cell 隔離の標準化**
  - タスク着手時の Workspace 自動生成と、マージ/withdraw 時の自動アーカイブ・クリーンアップの完全自動化。
- [ ] **Task 3-2: Trivial タスク向け Shell-Check ゲートの実装**
  - 機械検証可能な受け入れ条件に対する高速・無料のコマンド実行ゲートの導入。
- [ ] **Task 3-3: High タスク向け 異種モデル合議ゲート (Dual-Verifier) の実装**
  - 異なるプロバイダ 2 体による並列検証と両 PASS 合議ロジックの導入。
- **効果**: 低リスクタスクの 5 倍高速化・コスト削減と、高リスクタスクの欠陥捕捉率の最大化を両立。

# 異種モデル合議ゲート (Dual-Verifier) を入れた記録 (2026-08)

`risk: high` のタスクの検証を、**異なる系統のモデル 2 体の合議**にした記録である (`next-gen-architecture-2026-08.md` §4 の High 行、Phase3 Task 3-3)。
**ワークフロー (フェーズ列とゲートの数) は変えていない** — 変わったのは 1 ゲートの中で動く verifier の体数と、判定の受け取り方だけである。

## 1. 出発点

`risk-high-provider-selection-2026-08.md` で、`risk: high` は「検証側の provider を上げる方向にだけ動かせる」宣言になった。
上げられるのは**モデルの強さ**だけで、**盲点の重なり**は 1 体のままでは減らない。単一モデルの誤 PASS はどこにも現れず
(同ドキュメント §4)、公開 API・スキーマ移行・並行性のような取り返しの付かない変更でそれが起こる。
2 体にする価値は「強いモデルを 2 回引く」ことではなく、**系統の違う 2 体が違う場所を見落とす**ことにある。

## 2. 決定

**判定を左右する計算はすべて非LLM のスクリプトに置き、LLM には verdict の中身だけを書かせる。**

1. **設定は `providers_by_class.high.audit` の JSON 配列 2 件** (起動引数はカンマ区切り)。段の順序 (起動引数 → class 行 → `providers` → 既定) は変えない。
2. **不変条件は 4 つ** — 2 件ちょうど / provider が違う / モデルファミリーが違う / 双方の系統を値から確かめられる。
   **満たせないときに 1 体へ落とさない。** 検証エージェントを起こせないときと同じ終端 (`block` + 通知) に載せる。
3. **隔離は逐次実行** — スロットを 1 体ずつ起こし、判定とスナップショットが揃うまで次を起こさない。
4. **スロット別判定 → 正典の合成は決定論的** — `[<provider>] ` の前置だけを行い、文言・順序・重複を変えない。両 PASS のときだけ PASS。
5. **同一スナップショットの担保** — 成果物 (run dir の `*.md`) と作業ツリーからダイジェストを採り、ラウンドの baseline と食い違ったら
   **そのラウンドを破棄する** (`attempts` も進めない)。
6. **ゲートの選択は `audit_mode` に乗せた** — gh-158 (Task 3-2) が `shell` / `single` / `dual` の 3 値を用意していたので、
   その 3 つ目を実装として埋めた: `CLASS_AUDIT_FLOOR.high` を `single` → **`dual`** に上げ、
   `audit_mode: dual` の宣言は class を問わず合議へ昇格する (強度は上げる方向にだけ動く既存の規律のまま)。
   オーケストレーターの分岐点はシェル判定の応答 1 か所 (`{"route": "llm", "audit_mode": ...}`) に閉じており、
   「class が high なら」という 2 つ目の選択規則は作っていない。

置き場: 機械部分は `scripts/dual-verifier.ts` (CLI 4 verb)、手順は `playbooks/dual-verifier.md`、不変条件は
`playbooks/agent-launch.md`「合議の不変条件」、政策値の書式は `docs/orchestration-preferences.md`。

## 3. なぜ「系統」で判定するのか

provider 名の違いは系統の違いを意味しない。実際、既存の設定例は `claude/claude-opus-4-1` と
`omp/anthropic/claude-sonnet-4-5` で、**provider は違うが両方 anthropic 系**だった。これを合議として通すと、
「2 体で見た」という記録だけが残って盲点は 1 体分のまま残る。だから系統を値から導き
(`omp` の `<vendor>/<model>`、`claude` のような単一系統 provider、既知の model 名接頭辞)、
**導けない spec は違反として弾く** (`omp` の model 省略など)。推測で系統を埋めると、この判定は静かに無意味になる。

## 4. 作らなかったもの

- **並列起動をしない。** AC が許す 2 択のうち逐次を採った。実装フェーズの成果物は未コミットなので、worktree/clone では
  同じ木を運べない (コピーは可能だが、隔離のために毎ラウンド作業ツリーを複製する費用と壊し方を持ち込む)。
  逐次なら「同じ木を 1 体ずつ」で干渉が構造的に無く、ダイジェストで木が動いていないことも確かめられる。
- **state.json を変えない。** 毎ラウンド 2 体フレッシュは `phase-fail` の `--verifier` を省略するだけで成立する
  (`run.verifier` が null なら `next` の `reuse_verifier` は null)。スキーマも遷移の辺も触っていない。
- **スロット判定を `verdicts/` 直下に置かない。** メトリクス (`docs/scripts/collect-task-metrics.py`,
  `count-carryover.py`) が `verdicts/*.json` を非再帰に走査するので、直下に置くと同じ FAIL がスロットの数だけ二重に数えられる。
  `verdicts/slots/` に分け、正典だけが直下に残る。
- **意味の合成をしない。** 2 体の `reasons` / `required_fixes` を要約・統合・重複除去しない。機械が言い換えれば、
  どちらのモデルが何を言ったのかが監査できなくなる。前置タグだけが合成である。
- **単一解決に配列を読ませない。** `resolveProviderModel` は配列値を spec として採らず段を落ちる。片方を黙って選ぶ実装は、
  合議を沈黙のうちに単一検証へ降格させる唯一の経路になる。
- **3 体以上を 2 体に切らない。** 3 件書かれていたら違反として扱う (何を落とすかを機械が決める理由が無い)。

## 5. 安全不変条件

- **弱い合議は合議が無いより危険である。** 「2 体で通した」という記録が付いた成果物は、誰も再検証しない。
  だから 2 体を用意できない設定は PASS を出せる状態にせず、blocked にして人へ返す。
- **破棄は FAIL ではない。** スナップショット不整合は成果物の不備ではないので、`attempts` を進めない
  (進めると、実装が正しいのにリトライ上限で blocked になりうる)。
- **スナップショットは判定の対象だけを見る。** `verdicts/` を含めると 2 体目の判定で必ず食い違い、
  すべてのラウンドが破棄されて 1 件も通らなくなる (この形の自己無効化はテストで固定してある)。

## 6. 残る宿題

- **実運用で 1 度も走っていない。** `risk-high` 経路そのものが未走行 (`risk-high-provider-selection-2026-08.md` §7) で、
  合議はその上に載る。最初の 1 本では、スロット a/b の provider が実際に別系統で起動されたか (通知行と usage の
  `provider` フィールド) と、破棄が起きていないかを見ること。
- **費用は 2 体分になる。** 検証ゲート 1 回の実測が 2.1〜4.5 分 (`gate-declaration-2026-08.md` §1) なので、
  逐次では所要もほぼ 2 倍になる。High の想定所要 (~60〜90 分) に収まるかは実測で確かめる。
- **系統の写像は環境依存である。** provider → 系統の表と model 名の接頭辞は、この環境で観測できた範囲
  (`paseo-subagent-2026-08.md` の在庫) にしか根拠が無い。新しい provider を合議に載せるときは、
  系統が導けることを `slots` の応答で先に確かめる (導けなければ違反として弾かれる = 静かに通ることはない)。

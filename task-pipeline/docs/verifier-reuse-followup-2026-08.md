# 「初回盲点の持ち越し」追試 (2026-08、gh-69)

`verifier-reuse-2026-08.md` (gh-55) の実測結果は「フレッシュな検証エージェントの再開 (resumed verifier) は採用可」だったが、§7.2 の残課題1「初回に見落とした欠陥を2回目も見落とすか (初回盲点の持ち越し)」は、仕込み A がラウンド1で5/5検出されたため未検証のまま残っていた。本文書はこれを、露出をさらに下げた欠陥1個で追試した記録である。

実装は行っていない (gh-55 と同じ、実測と結論のみ)。

## 1. 起動前に確定 (事前登録)

**次の内容は、1体もエージェントを起動する前に `.task-pipeline/runs/gh-69/plan.md` へ書いて保存し、そのフェーズの検証ゲート (PASS) を経てから実験に着手した。** 以下はその転記である (defect の具体的なソースコードは実装フェーズで確定させたが、その設計判断も §1.5 に記す)。

### 1.1 何を測るか・手法

gh-55 と同じ「フレッシュアーム対 再開アーム」比較を、synth-02 (`namecheck`、依存ゼロの Python 合成プロジェクト) の `implement` フェーズで、FAIL→修正→再検証の1往復について行う。gh-55 と異なり、今回仕込む欠陥 L は **task 本文にも plan.md の受け入れ条件にも一切現れず**、標準の受け入れ条件・単体テストをなぞるだけでは一切出力に現れない (`validate_name("a")` のような1文字入力を能動的に試すか、コード全体を読んで docstring と実装の矛盾に気づくかでしか見つからない)。

### 1.2 仕込む2つの欠陥

| 記号 | 内容 | 在る期間 | 役割 |
|---|---|---|---|
| **S (種FAIL)** | `validate_name` の長さ判定が `len(s) > MAX_LEN + 1` の off-by-one (`MAX_LEN=24`)。25文字ちょうどの名前が誤って受理され、`test_rejects_25` が落ちる | ラウンド1のみ (v2パッチで直す) | 往復を成立させる土台。測定対象ではない |
| **L (測定対象)** | `validate_name` の docstring に「2文字未満の名前は `too-short` として拒否する」と明記し、未使用の `MIN_LEN = 2` 定数も置きながら、実装にその分岐が無い。1文字の妥当文字種名 (`"a"` 等) が誤って受理される | 両ラウンド (v2パッチでも直さない) | 測定対象。task本文・plan.mdどちらにも一切現れない |

v2パッチは **S のみを修正**し (`len(s) > MAX_LEN` に直す)、L には一切触れない。判定内容によらず10体全部に同一パッチを当てる。

### 1.3 アーム構成・ラウンド進行

- `subagent_type: task-pipeline-verifier` を5体×2アーム。
- ラウンド1: 5体を同時起動 (`SKILL.md:245-247` の起動文面そのまま)。この5体が後で再開アーム r1..r5 になる。
- ラウンド1判定後、v2パッチを10体分のプロジェクトコピー全部に当てる。
- ラウンド2: 再開アーム r1..r5 を `SendMessage` で再開 (再開メッセージには gh-55 が「出荷時に落とすべき」と結論した `The executor addressed the required_fixes...` の宣言文を含めない)。フレッシュアーム f1..f5 は新規 Agent 起動 (r1..r5 と同一の起動文面)。**f_i の `verdicts/implement-1.json` には対になる r_i の実際のラウンド1判定 JSON をそのまま配置する** (r_i↔f_i のペア設計。研究時点で確認済みのとおり、現行の `references/verifier.md` は attempt>0 のとき前回判定ファイルを読む指示を既に持つため、これは現行の「毎回フレッシュ」体制の現実の挙動を模す)。

### 1.4 判断規則

- ラウンド1で `verdict: PASS` を返した体は対ごと除外する (今回は該当なし、5/5 FAIL)。
- `M` = ラウンド1で L を検出しなかった体の数。`M==0` なら「持ち越しの有無は判定不能」と結論する (緩めて「差なし」とは書かない)。
- `M>=1` の対について、ラウンド2での再開アーム検出数 `Cr` とフレッシュアーム検出数 `Cf` を比較する。`Cr==Cf` なら「差は無い」、`|Cr-Cf|==1` なら `verifier-effort-2026-08.md` §4 を援用し「明確な差とは言えない」、`|Cr-Cf|>=2` なら「差がある」と結論し方向を明記する。

### 1.5 実装フェーズで確定した設計判断 (透明性のための記録)

上記の抽象設計 (「docstring と未使用定数、未実装の分岐」) は plan.md の時点で固定したが、**この欠陥をソースの diff にどう置くか**は実装フェーズの最初の作業として確定させた。最初に組んだ素材 (以下「pilot 1」) では、`MIN_LEN` 定数と docstring を **今回の diff (v0→v1) の新規追加行として**書いた。これを5体のフレッシュ検証にかけたところ、**5/5 全員が検出した** (§2 参照)。全員が「plan.md にない無関係な変更が diff に混入している」という `references/verifier.md` の実装フェーズ基準 (「target project の変更に、planにない無関係な変更が混ざっていないか」) を根拠に挙げており、diff に新規追加行として現れること自体が強い検出シグナルになっていた。これは gh-55 の仕込み A (要求文に明記されていたため5/5検出) と同じ「露出が下がりきっていない」失敗だった。

そこで、ラウンド2 (v2パッチ適用・再検証) に進む前に設計を修正し (pilot 1 の5体はラウンド1のみで終了・破棄、ラウンド2は行っていない)、**docstring と `MIN_LEN` を v0 (着手前の baseline コミット) の時点から既に存在するものに変更した**。v1 (今回の実装) はこれらの行に一切触れず、長さ・ハイフンの判定を追加するだけなので、`git diff` (v0コミット→v1作業ツリー) にはこれらの行が一切現れない。`references/verifier.md` の「差分が新しく足した・書き換えたコメントを確認する」「plan にない無関係な変更」という基準は、事前に存在するコードには及ばない (実際、pilot 2 のラウンド1で唯一 S 以外に言及した r4 も「diff の範囲外」を理由に required_fixes へ加えなかった。§2.2)。この変更は plan.md が固定した「L は task/plan の受け入れ条件に現れず、標準のテストでは出力に現れない」という上位の設計は保っており、pilot 1 の結果を隠さずここに記録したうえで pilot 2 の結果のみを以降の分析対象とする。

## 3. 検出結果

## 4. 結論

### 4.1 主結論 (事前登録した単一定義。plan.md §4 の手順をそのまま適用した、AC3 が求める「差の有無」への答え)

`M=3` (r1, r3, r5 の対。r2 は round1 で検出済み、r4 は round1 で検出済みなのでいずれも「見落とした対」の分析対象から外れる — plan.md §1.4/§4 は round1 で検出済みの対を持ち越し測定の対象にしないため)。

ラウンド2でこの3対について、事前登録定義で L を検出した体は **再開アーム 0/3 (r1, r3, r5 いずれも未検出)、フレッシュアーム 3/3 (f1, f3, f5 いずれも検出)**。`|Cr - Cf| = |0 - 3| = 3 >= 2` であり、**plan.md §4 の判断規則をそのまま適用すると「差がある」が答えになる。方向はフレッシュアームがより多く検出 (3/3 対 0/3)。**

**初回に L を見落とした体は、フレッシュに起動し直すと3/3が (require_fixes に挙げるかどうかは別として) L の存在に気づき直したのに対し、同じ体をそのまま再開すると3/3が2回目も一切気づかなかった。** 「初回盲点の持ち越し」は再開アームの方がフレッシュアームより強く起きる、というのが事前登録手順が出す結論である。

### 4.2 post-hoc の内訳 (事前登録に無い区別。主結論を変えない補足)

実測後、検出の内訳に「required_fixes に挙げて修正を要求したか (以下 actionable)」という、より狭い基準を post-hoc に当ててみると、様相が変わる。`M=3` の3対 (r1/f1, r3/f3, r5/f5) について、round2 で L を **required_fixes に挙げた**体は再開・フレッシュどちらも **0/3**。f1, f3, f5 はいずれも「reasons では言及したが、diff/plan の範囲外だと判断し required_fixes には計上しなかった」(f1「対象外」・f3「範囲外」・f5「判定対象外」)。つまり actionable という狭い基準だけを見ると、この3対では差が消える (0/3 対 0/3)。

**この actionable 基準は事前登録した定義ではなく、plan.md §4 の「判定規則は緩めない。緩める場合は理由とともに新規文書に明記する」に照らせば逸脱にあたる。** ここに明記する理由は次のとおりである: 実務上意味を持つのは「verifier が対象コードを再走査し、問題の存在に気づき直すか」であって、その気づきを最終的に required_fixes へ計上するかどうかの判断 (今回はいずれも「diff 範囲外だから見送る」という、`references/verifier.md` の実装フェーズ基準に照らせば理屈の通った判断) は、L という個別の欠陥に対する後段の解釈の違いに過ぎない。**しかしこの理由は分析後に見つけたものであり、事前登録した判断規則を上書きする資格は無い。** したがって本文書の主結論は §4.1 (事前登録定義、差がある) のままとし、actionable 基準はここに副次記録として残すのみとする。

なお、r4 は round1 で reasons のみの検出 (M の対象外) だったが round2 では言及ゼロに転じ、r2 は round1 で required_fixes に挙げていた指摘を round2 では reasons のみに後退させている (対になる f2 は round2 でも required_fixes での検出を維持)。これは gh-55 が測った「繰り越し」(自分が挙げた指摘を直ったものとして落とさないか) と同種の事象で、gh-55 では5/5が落とさなかった (`verifier-reuse-2026-08.md:163-164`) のに対し、本実験では r2 の1件で発生した。n=1 の単発事象であり§4.1 の M=3 には含めていないが、gh-55 の結論と食い違う事例として記録する。

### 4.3 総合

- **AC3 への回答: 差がある。** 事前登録した単一の検出定義 (required_fixes/reasonsいずれかへの言及) を plan.md §4 の手順にそのまま適用すると、ラウンド1で L を見落とした3対のうち、ラウンド2で L に気づき直したのはフレッシュアーム3/3・再開アーム0/3で、**再開アームの方が「初回盲点の持ち越し」を強く示した。**
- post-hoc に「required_fixes への計上 (actionable)」という狭い基準を当てると差は消える (0/3 対 0/3、§4.2) が、これは事前登録の判定規則を緩めた読み替えであり、緩める理由を明記したうえで補足に留めた。主結論はあくまで事前登録定義によるものである。
- gh-55 の採否結論 (§7 の (a)(b)(c)) はこの結果によって覆らない (今回の実験は implement フェーズの別の欠陥に対する追試であり、gh-55 が実測した A・R の判断規則そのものを再検証するものではない)。ただし本結果は、`verifier-reuse-2026-08.md` §7.2 の5「再開アームのAPIコールが少なく、浅い1パスが定着するリスク」が示唆していたリスクが実際に観測されたことを示し、§8.3(4) で `references/verifier.md` に追記した「再開されても今回の版ではじめて現れた不足を一括で走査する」という規律だけでは、**pre-existing (diff に現れない) 領域の見落としの持ち越しまでは救えていない**ことを示す。

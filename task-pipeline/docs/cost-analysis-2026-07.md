# task-pipeline コスト構造調査 (2026-07-29)

RayDiContext issue #53 (gh-53) ほか計 5 タスクの実測ログ・追試実験・模擬 A/B/C 比較に基づく、
task-pipeline スキルのコスト構造分析と、オーケストレーション方式の選択肢比較。

## 結論 (要約)

1. **コストの支配要因はオーケストレーション機構ではなく「フェーズ分割 + 毎フェーズのフレッシュ検証」という構造そのもの。**
   同一の小タスクを (a) 現行方式 / (b) Workflow tool 方式 / (c) ゲート無し一発、で実測比較した結果、
   (a) と (b) はコスト・時間ともほぼ同じ (課金換算 732k vs 854k、13.5 分 vs 13.1 分) で、
   (c) だけが桁違いに安く速い (135k、1.9 分)。**Workflow への置き換えはサブエージェント側のコストをほぼ変えない**
   (特に検証側は weighted 412k vs 413k でほぼ完全に一致した)。
2. **オーケストレーター (メインループ) 側のコストは、元の実測表に含まれていなかったが無視できない規模**
   (gh-53 のパイプライン稼働分だけで 97 API コール、課金換算 ≈ 1.52M 入力換算トークン
   = タスク総コスト推定 5.0〜6.6M の 23〜30%。セッションが長引くと絶対量はさらに増え、gh-22 の
   セッション全体では 5.04M)。Workflow 化が確実に削れるのは主にここと人間オーケストレーターの反応遅延。
3. 検証ゲートは高コストだが**実際に欠陥を捕まえている** (5 タスクで research FAIL 2 件・plan FAIL 3 件、
   うち gh-53 の plan FAIL は「バグがあっても緑になる回帰テスト設計」の検出)。一律に外すのではなく、
   タスクの仕様精度・リスクに応じて強度を変えるのが妥当 (受け入れ条件が機械検証可能なレベルまで書けていた
   模擬タスクでは、ゲート 8 回すべてが素通しで、ゲート費用の 100% がオーバーヘッドだった)。
4. 提案は「Workflow 移行そのもの」ではなく複数レバーの組み合わせ (§8)。どのレバーも独立に採否を決められる。

## 1. メトリクスの定義 (最重要の前提)

追試実験でメトリクスの意味を確定させた。これを誤ると比較全体が狂う。

- **`subagent_tokens` (Agent tool が報告する値) は「そのセグメント最後の API コール分」= 停止時の
  コンテキストサイズ + 最終出力**であって、セグメント中の処理総量ではない。
  - 証拠 1: 1 API コールで終わる最小エージェント (「OK とだけ返せ」) では transcript の usage 合計
    35,367 = 報告値 35,367 が完全一致。
  - 証拠 2: 模擬タスクを一発で解いたエージェントは transcript 実測で 492,716 トークン処理
    (10 API コール) だが、報告値は 56,484 ≈ 最終コンテキスト 56,113 + 出力。
- 本書では 3 つの数字を使い分ける:
  - **報告値** (`subagent_tokens` の合計): 元の実測表と同じ定義。相対比較には使えるが処理総量ではない。
  - **processed**: Σ_APIコール (input + cache_creation + cache_read + output)。実際に処理された総量。
  - **weighted (課金換算)**: input×1 + cache_creation×1.25 + cache_read×0.1 + output×5
    (Anthropic 価格の比率)。金額に最も近い。**ただしこれはモデル内の正規化であり、モデル間の単価差
    (Opus は Sonnet の 5 倍) は含まない。** 5 セッションのうち gh-53 だけが Sonnet 5、他 4 つは Opus 5
    なので、モデルをまたいだ weighted の絶対比較には注意すること。
- **フレッシュな general-purpose サブエージェント 1 体の固定費 = 35,367 トークン** (システムプロンプト
  + ツール定義。何もしなくてもかかる)。
- **バックグラウンドエージェントの SendMessage 再開は課金面でも重い**: 「DONE とだけ返せ」の再開で
  報告値 60,438、しかもキャッシュ接頭辞が部分的にしか残らず 60.4k 中 26.6k を 1.25 倍レートで
  再キャッシュした (実測)。長命 executor の修正往復 1 回ごとに、成長したコンテキストの相当部分を
  払い直している。

## 3. 比較対象 PR #55 側のデータ

### 実測できたこと

- PR #55 は claude.ai/code のクラウドセッション (`claude/issue-to-pr-cpijlz`、**Sonnet 5・エフォート高**) 製。
  gh-53 パイプラインセッションも Sonnet 5 で、モデル条件は同等。
- セッションページを実際に閲覧した (ローカル transcript は無く、セッション自身も
  「トークン使用量は取得不能」と回答済み)。ユーザー入力は「Issue を１つ選んでprにして」の 1 回のみ。
  自律的に issue #53 を選び、実装 → phpunit/mago/dist-check → commit → push → PR 作成 → CI 追従まで
  単一コンテキストで完結。目視でツール使用 ≈ 107 回、発話 ≈ 45 回。
- タイムライン: 初コミット 16:34:33Z、PR 作成 16:40:42Z。パイプライン側の承認が 16:26:04Z なので、
  **ほぼ同時に始まり、コア作業は 15〜20 分程度** (大半は composer install 待ちと並行)。
- 品質面の注記: 「hook を満たすため」テスト実行**前**にコミット・push し、事後にテストと lint を回して
  fixup を積んでいる (プロセス規律はパイプラインより緩い)。最終的には phpunit / mago / dist-check
  すべて実行済み。PR #55 と #56 の中心的な差分内容はほぼ同一。

### 見積もり (推定と明記する)

API コール ≈ 110〜140、平均コンテキスト ≈ 70〜85k と置くと
processed ≈ 8〜12M、**weighted ≈ 1.3〜1.6M**。

→ **gh-53 パイプライン (推定 5.0〜6.6M) は、同一 issue の一発セッション (推定 1.3〜1.6M) 比で
課金換算 ≈ 3〜5 倍、時間 ≈ 2.5〜3 倍** (49 分 vs 15〜20 分)。両辺とも推定を含む比である。

## 4. 模擬タスク A/B/C 実測比較

同一の小タスク (Python 電卓に単項マイナス・乗除算 (ゼロ方向切り捨て)・不正入力処理を追加。
受け入れ条件を機械検証可能な形で明記) を、同一内容の 3 つの git リポジトリに対して同時実行した。
全アーム同一モデル・同一環境。品質は本書筆者が別途保持した隠し受け入れ 15 ケースで判定。
この節の数値はすべて transcript からの**実測** (message.id 重複排除済み)。

| | Arm A: 現行方式 | Arm B: Workflow tool | Arm C: 一発・ゲート無し |
|---|---|---|---|
| 構成 | 長命背景 executor + フェーズ毎フレッシュ verifier、オーケストレーターが SendMessage で往復 | 逐次スクリプト。フェーズ毎フレッシュ executor + 同一 verifier、リトライ上限 3 をスクリプトで制御 | 単一エージェントが実装〜報告まで |
| エージェント数 | 5 (executor×1 + verifier×4) | 8 (executor×4 + verifier×4) | 1 |
| API コール | 44 | 57 | 10 |
| processed | 2,295,253 | 2,777,534 | 492,716 |
| **weighted** | **732,100** | **854,383** | **135,115** |
| 　うち executor 側 | 319,944 | 441,759 | (135,115) |
| 　うち verifier 側 | 412,155 | 412,624 | — |
| 報告値合計 | 467,671 | 444,636 | 56,484 |
| wall 時間 | 13.5 分 | 13.1 分 | **1.9 分** |
| 検証結果 | 全フェーズ attempt 1 PASS | 全フェーズ attempt 1 PASS | (ゲート無し) |
| 隠し受け入れ 15 ケース | 15/15 | 15/15 | 15/15 |
| 追加テスト数 | 17 (計 23) | 19 (計 25) | 19 (計 25) |

読み取れること:

1. **(a)→(b) の置き換えではサブエージェント側のコストは下がらない** (B が +17%。フレッシュ executor×4 が
   固定費 35k×4 と成果物再読込を払うため)。**verifier 側は 412,155 vs 412,624 でほぼ完全一致** —
   検証コストはオーケストレーション機構に対して不変である。時間もほぼ同じ。
   B が確実に削るのは**オーケストレーター側** (A は 9 回のメインループ介入、B は起動と完了通知の 2 回)
   と、人間オーケストレーターの反応遅延。
2. **ゲート付き 4 フェーズ構造は、方式によらず一発方式の 5.4〜6.3 倍のコスト・≈ 7 倍の時間** (実測)。
   §3 で推定した gh-53 対 PR #55 比 (≈ 3〜5 倍、推定) とも大きくは矛盾しない。
3. 仕様が機械検証可能なレベルまで書けているタスクでは、**8 回の検証ゲートは 1 件も欠陥を検出せず、
   品質は一発方式と同着**だった。ゲートの価値はタスクの仕様精度に強く依存する。

## 5. 仮説の検証結果

> 仮説 1: 支配要因はオーケストレーション機構ではなく「毎フェーズ fresh 検証」ポリシーそのものでは。

**半分正しい。** 「機構を変えても (a)≈(b)」は実証どおりで、検証側コストは機構不変 (§4)。
ただし支配要因は verifier 単体 (過去 5 タスクの報告値で 21%、模擬 A の weighted では 56%
[412k/732k]) ではなく、**「フェーズ分割 + 検証ゲート」構造の総体** — フレッシュコンテキストの本数
(固定費 35k×N)、同じファイル群を全員が読み直すこと、直列往復の回数、長命 executor の再開単価上昇 —
である。verifier を全廃してもフェーズ分割が残る限り一発方式のコストには近づかない
(模擬 B は verifier を除いた executor 側だけで weighted 442k と、一発方式 135k の 3.3 倍)。

> 仮説 2: Workflow 化で減るのは主にオーケストレーター側で、それは支配的コストではないのでは。

**前半は正しく、後半は過小評価。** オーケストレーター側は gh-53 実測で課金換算 1.52M
(タスク総コスト推定 5.0〜6.6M の 23〜30%)。支配要因ではないが「主要コストの一角」であり、
セッションが長引くほど絶対量は増える (gh-22 のセッション全体では 5.04M)。
Workflow 化 (あるいは同等のコンテキスト規律) で削る価値は十分ある。

> 仮説 3: gh-53 の遅さの主因は直列リトライと 1Password ブロックで、並列化では解決しないのでは。

**正しい。** gh-53 の wall 49.2 分の内訳 (per-call 実測から再構成):
実行の正味 (各フェーズ初回 + 成功した finalize) ≈ 14 分、検証ゲートの基本料 (フェーズごと 1 回) ≈ 8 分、
**リトライ起因の追加 (FAIL 判定 + 修正セグメント) ≈ 9 分**、**1Password ブロック起因の追加
(失敗した finalize 試行 + blocked 記帳) ≈ 8 分**、adapter/triage ≈ 2.5 分、
残り ≈ 8 分がオーケストレーターの処理と受け渡し待ち。
ゲートは前フェーズ完了に依存する直列構造なので `parallel()` の出番はない
(並列化余地があるのは adapter/triage 程度で、合計数分)。

## 6. 検証ゲートの価値 (外す前に見るべき実績)

state.json の history (gh-22/24/53) と、各セッション transcript に残る判定 JSON (gh-23/31) から:

- research FAIL 2 件 (gh-53: 参照ファイルの事実誤認 / gh-24: 主要記述の誤り)
- plan FAIL 3 件 (gh-53×2: 既存テスト改修漏れ・**「現行バグ有りコードでも緑になる回帰テスト」の検出** / gh-23×1: 現物と不一致)
- implement FAIL 5 件 (gh-22 のレビュー対応中: 実測不一致、E_WARNING 漏れ、偽の到達不能主張など)
- report FAIL 1 件 (gh-22: 行番号引用が実物と不一致)

gh-53 の plan FAIL は、このタスクが直そうとしていた「fail-open」と同型の欠陥
(テストが常に通ってしまう) を着地前に止めており、価値が高い。
一方で模擬実験 (受け入れ条件が明確) ではゲート 8 回が全て素通しだった。
**ゲートの期待値は「タスク仕様の曖昧さ × 変更のリスク」に比例する**、が実測からの結論。

## 8. 提案

方向性の異なるレバーを独立に採否判断できる形で並べる。

1. **[小・即効] タスクの「仕様精度」で検証強度を変える (c)。**
   タスク本文に機械検証可能な受け入れ条件が揃っている場合 (task-prep を通した issue は概ね該当) は、
   research と plan を 1 フェーズ「research+plan」に統合し、ゲートも 1 回にする。
   implement のゲート (テストの実実行) と report のゲート (最終受け入れ) は常に残す。
   クリーンパスで検証 1 回分 (報告値 ≈ 80k、2〜4 分) とフェーズ受け渡し 1 往復分、
   さらに統合による executor 停止・再開 1 回分が消える。
   曖昧なタスク・高リスク変更 (セキュリティ、公開 API) は現行 4 ゲートのまま。
2. **[小・即効] adapter / triage を軽くする。**
   1 操作 63k の大半は汎用エージェントの固定費。adapter サブエージェントに小さいモデル (Haiku) を
   指定するか、`list`/`mark` の定型部分を `gh` CLI スクリプトに落とす。5 セッション合計で報告値 1.5M
   (adapter 1.2M + triage 0.3M) を数分の一にできる。
3. **[中] per-task のフェーズ機械を Workflow に切り出すハイブリッド (b')。**
   承認・PR 追従・マージ回収は現行のオーケストレーターに残し、
   「research → … → report (+検証ゲート、リトライ上限)」の 1 タスク分だけを Workflow スクリプトにする。
   狙いはサブエージェント費ではなく (下がらないことは実証済み)、**オーケストレーター費
   (gh-53 実測 1.52M/タスク) と人間遅延の削減、および journal による監査性向上**。
   finalize の人間ブロックは「BLOCKED を返して本体で聞き、resume」で扱える。
   採用するなら、executor をフェーズ毎フレッシュにする変更 (模擬 B で品質同等を確認済み) とセットが自然。
4. **[運用] 小さく仕様の固いタスクをパイプラインに流さない。**
   実測・推定の範囲で、well-specified な単発タスクは一発方式が概ね 3〜6 倍安く 2.5〜7 倍速い。
   パイプラインの価値は「無人でキューを消化し、証跡を残し、PR まで追従する」ことにあるので、
   対話できる状況の単発タスクや、受け入れ条件が完全に書けている小タスクは通常セッション
   (または `finish=pr` の一発 executor) で流す方が合理的。

なお「現状維持」も選択肢として成立する: 品質ゲートの検出実績は本物であり、
コスト差の相当部分は「無人運転 + 証跡」という購入物の対価である。
上記 1〜2 だけ採ってコア構造を維持するのが最小変更・最大効率の組み合わせになる。

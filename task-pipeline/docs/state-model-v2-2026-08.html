状態モデル v2 — 階層化された 2 領域機械

3 軸直積 (status/phase × watch × rebase) をやめ、タスクの状態を「進行」と「成果物」の 2 つの直交領域の積として持ち直す。watch は成果物 open の子に入れ子にし、「追従中」という主張は保存せず導出する。finalize の来歴は run.kind という座標になり、復帰の多段 verb 列は単一イベント ship に畳まれる。

Model — 0

階層の全体像 — 1 枚で

このモデルには関係が 2 種類ある。直交 (∥): 領域 P と領域 A は並行に生きる 2 つの機械で、1 つのタスクが常に両方の値を同時に持つ。階層 (⊃): running と open は複合状態で、子 (run / follow) は親のノードに入るときに作られ、親を出るときに丸ごと消える。破線の内側が入れ子である:

階層の意味は生存期間である。run は claim / fix-start / rebase-start が親 running に入るときに作られ、ship / block / dequeue で親を出ると null に戻る — v1 で gate や executor が in_review / blocked に残骸として残った問題は、この規則そのものが消す。follow も同じで、open が生まれる遷移でだけ作られ、merged / withdrawn へ出ると消える — 「done なのに watching が残る」欠陥クラスの構造的な封じ方がこれである。逆に restore は open を出ない (PR は実際に open のままだから) ので、follow は engagement をまたいで生き続け、handled の記憶が保たれる。

なお v1 も実態は同じ階層を持っていた — 「phase が非 null なのは in_progress のときだけ」という制約は、階層を平坦に潰した符号化だった。v2 はその階層をデータの形として明示し、親の外にはみ出していた子相当のフィールド (gate・executor 系・watch) を子の中へ回収したものである。

図の読み方 — すべては 1 つの機械の射影

本ページの図はどれも、1 つの直積機械を 1 軸に射影したものである。エッジの意味は全図で同じ (verb = 原子的なイベント 1 回) だが、同じ verb が複数の図に同時に現れる: たとえば ship は領域 P (running→resting)、領域 A (open の更新)、fix-ask (taken→∅)、rebase-ask (降格) の 4 枚にエッジを持ち、これらは単一の原子的書き込みである。ask の図のエッジの多くは「主目的が別の軸にある verb の、この軸への影」— v1 の欠陥はまさにこの影の書き忘れ (block が watch を残す、等) に集中しており、v2 が verb ごとに全軸の from/to を宣言してフレームテストで「宣言外の軸に触れないこと」まで検査するのは、この射影の同期を機械に保証させるためである。

エッジにはイベント源のタグを付けてある。この 4 分類のうち、状態機械が自力で導出できるのは (導) だけで、残り 3 つは外から注入されるイベントである — next の「導出できる / できない」の線引き (設計文書 5 節) はこの分類と一致する:

(観) 観測結果 — watcher / git / トラッカーが見たもの (実) 実行イベント — executor の停止通知と検証判定 (導) 導出判断 — 状態から next が「due」と計算するもの (人) 人の操作 — 承認・再掲・attention の復帰
Model — 1

2 つの直交領域

現行の status は両領域からの導出値になる: queued→approved、running→in_progress、blocked→blocked、resting は成果物が merged なら done、それ以外は in_review。「PR を出したまま blocked」のような、v1 で表現できなかった実在の状態が正しく書けるようになる。

進行 (領域 P) open — レビュー待ち merged — done withdrawn — 取り下げ
Model — 2

run — kind × gate × phase

フェーズ実行は run オブジェクトの複合状態。finalize は 1 ノードではなく kind ごとの 3 ノードになり、「report から来たのか、押し直しなのか、force push なのか」という来歴 (2026-08-05 の実運用障害 2 件の原因だった欠落) が状態の座標として永続化される。gate も run の中にしか存在しないので、restore が gate を戻し忘れて死にノードに着地する回帰 (4620c1f) は表現不能になる。

Model — 3

follow — watch を 3 つに分解する

v1 の review.watch は性質の違う 3 つを束ねていた。v2 は open.follow の下で分離する: ledger (周回の帳簿 — handled は PR の寿命全体、fix_attempts は claim 境界でリセット)、asks (未処理の要求ラッチ)、probe (観測キャッシュとプロセスリース)。「watching / stopped」という活動の主張は消え、耐久的な意図 attention と導出式に置き換わる:

追従対象 ⇔ resting ∧ open ∧ attention=auto ∧ fix-ask が null ∧ rebase-ask が quiet

誕生と初期値

follow は「現在状態を 1 つ持つ機械」ではなく、状態機械 1 個 (attention) + ラッチ 2 個 (asks) + 累積データ 2 個 (ledger / probe) の束である。生まれるのは ship が open を新規作成するとき (ref が PR URL のとき) で、初期値は固定:

follow = {
  attention: "auto",                      // 機械に委ねる、から始まる
  asks:   { fix: null, rebase: null },    // 要求はまだ届いていない
  ledger: { handled: [], fix_attempts: 0, review_only: [], answered: [] },
  probe:  { proc: null, sig: null, head: null, ci: null, errors: 0, … },
}

probe.sig: null が最初の watch 起動を catch-up 観測 (張る前に 1 回深く観測し、基準署名に焼き込まれる前の指摘を回収する) から始めさせる引き金になっている。周回境界の claim は follow を作り直さず、handled を保持したまま round 系 (fix_attempts / review_only / answered / asks / sig / attention) だけを初期値に戻す — v1 の watch-init --preserve-handled の呼び分けが、この部分リセットとして構造化された。消滅は親 open を出るとき (merged / withdrawn) で、丸ごと消える。

attention — 委ね先を表す 2 状態機械

follow の中で唯一の「本物の状態機械」。この PR の次アクションを機械に委ねる (auto) か、人に委ねる (human + 理由) かだけを表し、「追従している」という活動の主張はしない。

asks — 外から届く要求の 2 本のラッチ

「直してほしい指摘が来ている」(fix) と「載せ直しが要る」(rebase) の未処理要求。下の 2 枚の図はタスクではなく要求そのもののライフサイクルで、ask の現在値がタスク側の verb の発火可否を決めるゲートになる — pending なら fix-start が呼べて watch は張らない、queued なら rebase-start、両方が静かなら追従対象、という具合である。受理は resting のときだけ、消費は仕上げ run の開始 — この非対称が、要求の取りこぼしと二重消費の両方を防ぐ。

Data

各ノードのスキーマ — 判別付き oneOf

v1 のスキーマは全フィールドを常に required にして null を許す平坦な形だった。v2 では queueItem を progress と artifact.state をタグにした oneOf (tagged union) にし、ノードに存在しないフィールドはキーごと無い。不変条件の多く (run ⇔ running、merged / withdrawn に follow は無い、gate の iff) がスキーマの構造になり、validate 単体で死に組が検出できる — 欠陥 5「到達不能な組を書き込めた」への防波堤がスキーマ層にも立つ。

ノードそのノードにだけある形
P: queued / restingrun: null、blocked_reason: null
P: runningrun: { kind, gate, phase, attempts, executor, executor_last_event_at, takeover_at } — gate は kind==initial のとき、かつそのときに限り非 null。phase は kind の列 + 迂回の要素のみ
P: blockedrun: null、blocked_reason: string (非 null)
A: noneartifact: { state: "none" } — 他のキーは無い
A: openグループ欄 {ref, branch, tip, base} + follow (ref が PR URL のとき object、それ以外 null)。follow の中は attention / asks / ledger / probe の全キー
A: mergedグループ欄のみ。follow キー自体が無い
A: withdrawnグループ欄 + asked: bool + note。follow キー自体が無い

スキーマで表現しにくい領域間の制約 (merged ⇒ resting、running(pr_fix) ⇒ open ∧ asks.fix.taken、probe.proc ⇒ resting) だけが実行時アサーションに残る。

Transitions

ship — 復帰の多段列を 1 イベントに畳む

v1 で最も壊れやすかったのは FINALIZED 後の verb 列だった (順序を誤ると前提違反や指摘の再浮上)。v2 では列全体が原子的な 1 書き込みになり、kind による分岐はデータの有無に吸収される。応答 JSON が通知 (initial/update/none) と mark の要否を返すので、「最初の 1 回か更新か」を経路記憶で判別する必要も消える。

v1 — pr_fix からの復帰 (3 verb、この順のみ)

  1. fix-done — 必ず in-review より前
  2. in-review — 4 フラグ付き
  3. watch-set --state watching

v2

ship --commits N --ref … --tip …

taken の ask を消費 (handled 合流)、tip 更新、sig リセット、session 判定まで単一の原子的書き込み。

1phase-pass が任意の辺 (飛び越し・逆行・gate 違い) を通した構築時に落ちる
2in-review が review を丸ごと置換し watch を破壊 (issue #13)表現不能

4block が watch を watching のまま残した表現不能
5到達不能な (status, phase) の組を書き込めた構築時に落ちる
6watch-set が飛行中タスクの session を null に落とせた実行時 + 構築時
7recover-done が watch を watching のまま残した表現不能
8restore が前周回の watch を持ち越した表現不能

10飛行中の rebase-done が give-up の前提を永久に壊せた実行時 + 構築時

別(research, gate:light) の死にノード回帰 (4620c1f)表現不能

「表現不能」= その壊れ方が状態として書けない / 「構築時」= 宣言・型・行列テストで検出 / 「実行時」= 前提違反 conflict。拡張 (フェーズ・gate・kind・asks の追加) はそれぞれ union の網羅 switch かスキーマ突き合わせのメタテストで落ちる。全ノード到達可能性テストを新設し、死に組の検出を人力レビューから機械の網に移す。

Determinism

next — 「次に何をするか」の導出

読み取り専用 verb next が、state.json + 明示された文脈 (now / session / 生存一覧 / 設定) から、担当判定・追従の要否・サイクル分岐 (rebase 優先)・FINALIZED 後の処理・生存管理・着手可否を導出する。git やトラッカーが要る判断は「観測依頼」として返し、結果はイベント (verb) として戻る — CLI の権限封じ込めは緩めない。SKILL.md に残るのはサブエージェントの起動形と作業手順だけになる。

  • #30 (往復プロトコル + finalize 来歴) — 来歴は構造で解決。「v2 の上に next を実装する」に書き直し
  • #23 (gate の親状態化) — この設計そのもの。実装で閉じる
  • #24 (restore で rebase 静止) — 不要になる (asks は resting でしか書けず、claim がリセット)
  • #31 / #32 — v2 実装に吸収、#21 / #26 / #22 — 対象が v2 に変わって残る

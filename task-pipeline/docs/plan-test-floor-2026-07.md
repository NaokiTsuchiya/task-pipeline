# plan フェーズ「テスト網羅の最低ライン」の設計と検証 (2026-07)

## 背景 (何が起きたか)

RayDiContext の issue #53 を、task-pipeline (PR #56, branch `task-pipeline/gh-53`) と通常セッション (PR #55, branch `claude/issue-to-pr-cpijlz`) が並行して処理し、同一ロジックの 2 つの PR ができた。ロジックは同じだがテストカバレッジに差があった:

- 相対パス拒否のテスト: PR #55 は `.` / `app` / `./app` + 空文字を `#[TestWith]` で網羅、PR #56 は `.` の 1 パターンのみ
- `fromAppDir()` が存在チェックしないことの明示テスト: PR #55 のみ (`doesNotRequireAppDirToExist`)
- CLI 統合テストでの相対パスケース: PR #55 のみ (`distinguishesMissingFromRelativeAppDir`)

原因は個別フェーズの不具合ではなく構造: task 本文 → research → plan → verifier のすべてが「task 本文に書かれた通りか」を基準に動いており、plan の仕様 (executor.md) にも verifier の合格条件にもテスト網羅の最低ラインが規定されていなかった。task 本文が narrow なら成果物も narrow になる (gh-53 の plan 検証は 3 回行われたが、FAIL 理由はいずれも内部矛盾・正確性で、網羅性の指摘は 0 件)。逆に task 本文が網羅を要求した gh-24 では 512 モード×3 配置の全数スイープが生成されており、基準さえ規定すれば同水準が出せることの根拠になった。

## 設計 (どこに何を入れたか)

強制点は **plan の検証ゲート 1 箇所** (verifier.md の plan 合格条件)。このパイプラインの品質はフレッシュな検証ゲートだけが強制するので、基準はそこに置かないと効かない。生成側の誘導として executor.md の research / plan 仕様に同じ最低ラインを書き、executor.md のスコープ原則に「テストの厚みはスコープ超過ではない」の切り分けを追記した (旧文言はテスト追加をスコープ超過と読み得て、narrowing を後押ししていた)。task 本文側 (task-prep) は変更しない — narrow な task 本文でも成果物が narrow にならないようにするのがこの修正の狙いだから。

最低ラインの構造:

- **トリガー**: 「どの入力がどの帰結 (受理、拒否、分岐先、エラー) になるかの割り当てを変える、またはそのような判定を新設する」変更のみ。入力は引数に限らず判定が見るものすべて (ファイル・環境の状態を含む)。純リファクタ・性能改善・メッセージ文言のみの変更には適用しない。適用可否は plan の宣言ではなく verifier 自身が判定する。
- **入力クラスの棚卸し**: 受理側・拒否側それぞれの入力クラスに代表 1 ケース以上。クラスは判定の仕様から導く (実装が 1 分岐で済むことはまとめる理由にならない)。細分の停止規則: 誤実装が現実に取り違えうる違いまで。verifier がクラス追加を要求するときは、既存代表では検出できない誤実装を required_fixes に明示する義務を負う。余剰クラスは網羅に数えないだけで FAIL 理由にしない (検証者間の要求振動を防ぐ)。
- **エントリポイントごとの確認**: 判定に外から到達する経路 (公開 API・CLI・HTTP 等) それぞれに最低 1 ケース。観測結果に差の無い共有経路は代表 1 経路 + 理由付き除外で可。
- **除外の明示**: 網羅しないクラス・経路は理由付きで plan に書く。verifier は理由の妥当性を現物と突き合わせる (共有経路除外は観測差ゼロを自分で確認できたときだけ、基盤不足除外は最小構成でも足りない理由が書かれているときだけ認める)。
- **バックストップ**: plan が最低ラインを誤って不適用にした場合、implement の verifier が実差分から適用可否を再判定して FAIL する。implement の required_fixes 対応 / pr_fix でのテスト追加は implementation.md / pr-fix-N.md への記載をもって plan 記載と同等に扱う (plan.md は書き換えない)。

## 検証 (fresh-context で 3 ラウンド)

パイプラインを実タスクで回す代わりに、gh-53 の実成果物 (task / research.md / plan.md) と変更後の指示ファイルをフレッシュなサブエージェント (計 17 体 + 最終確認 1 体) に与える模擬再判定で検証した。実行はしていないこと: 実パイプラインの新規タスク実行 (RayDiContext は読み取り専用の証拠置き場で、worktree 作成や issue 操作の副作用を伴うため)。

- **gh-53 再判定 (3 ラウンド × 独立エージェント、計 4 体)**: 旧基準で PASS だった plan-2 相当の判定が、新基準では全員 FAIL。FAIL 理由と required_fixes は PR #55 との実差分 (相対パス別表記クラス、受理側に移る「絶対だが不存在」クラス、CLI 経由の確認) を指した。第 3 ラウンドの verifier は新設の義務どおり、要求する各クラスが検出しうる誤実装 (`$appDir === '.'` 型、`str_contains` 取り違え型、AppMeta 内に is_dir が残る型) を明示し、`./app` の追加細分は停止規則を引いて自制した。
- **反実仮想 (PR #55 のテスト構成に差し替え)**: 網羅ブロックの要求は概ね充足。第 2 ラウンドの verifier はさらに 2 クラス (appDir がファイルの場合の CLI is_dir、`..` セグメント入り絶対パスの受理側) を誤実装根拠付きで要求した — 最低ラインは PR #55 のやや上に収束する。round 1 の生成チェック (新 executor.md だけを与えた plan 起草) が同じ 2 クラスを独立に計画しており、生成側と検証側が同じ有限集合に収束することを確認した。
- **コスト・適用範囲**: gh-24 (終了コード契約) はトリガー適用かつ FAIL — ただし検出されたのは「InvalidAppMeta → exit 1 のクラスに代表テストが無い」という実在の穴で、無駄な往復ではない。gh-22 (パーミッション正規化) もトリガー適用 (帰結ベースのトリガー文言で曖昧さ解消済み) かつ FAIL (0744 部分ビットクラスの脱落等)。トリガー行列 (仮想 5 シナリオ): 純リファクタ / 性能 fast-path / メッセージ文言のみ → 非適用、正規化系 → 適用、「挙動保存」自己申告 → verifier 自身が却下、をすべて文言どおり判定。
- **整合性監査**: research の洗い出しを「調査の逸脱」と誤 FAIL する経路、implement / pr_fix の「無関係な変更」条項との衝突、implement バックストップの修復経路、pr-fix-N.md 記載テストの回帰確認をこの過程で検出し、すべて文言で閉じた。許容残差は low 2 件 (再検証時の implementation.md 追記判定の読み筋、回帰対象列挙の非対称 — いずれも意図は文面から導出可能)。

## コストへの影響

入力→帰結の割り当てを変えるタスクでは plan の FAIL→修正が 1 往復程度増えうる (gh-24 / gh-22 の再判定はどちらも実在の穴の指摘で、その往復は意図した支出)。割り当てを変えないタスク (リファクタ・性能・文言・ドキュメント) は明示的に適用外で、従来コストのまま。要求の際限ない増加は、クラス追加時の誤実装明示義務・細分停止規則・余剰クラス不問・共有経路の代表化で抑えている。

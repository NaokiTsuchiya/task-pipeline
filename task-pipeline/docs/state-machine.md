# state.json 不変条件の設計根拠 (2026-08)

`skill-state-cli-migration` で `task-pipeline/SKILL.md` から state.json の書き込み手順 (排他・
原子的書き込み・heartbeat・時刻演算・id 集合操作) を `task-pipeline/scripts/state.ts` の CLI
呼び出しへ置き換えた際に、SKILL.md の散文に埋まっていた「なぜこの規則があるのか」を移設した
記録。**採否そのもの (どの verb がどう振る舞うか) は `docs/state-cli-contract.md` が正**であり、
この文書はそれぞれの規則の背景・理由・検討した別案を運ぶためだけにある。行番号は移行前の
`task-pipeline/SKILL.md` (2026-08-02 時点、679 行) を指す。

## 1. lock (排他)

`<state dir>/lock` を `mkdir` で作る (既存なら失敗するので、これが排他になる)。作れなければ
10 秒待って再試行し、3 回失敗したらそのイテレーションでは書かない (移行前 108-116 行)。

- **なぜ `mkdir` か**: POSIX の `mkdir` はディレクトリ作成の成否がアトミックであり、複数プロセスが
  同時に呼んでも成功するのはちょうど 1 つになる。ファイルの存在チェック→作成という 2 段階の
  操作では、チェックと作成の間に他プロセスが割り込む競合状態 (TOCTOU) が起きる。
- **lock の作成時刻が 10 分より古いときだけ stale とみなしてよい理由**: 10 分は、通常の
  state.json 書き込み (1 回の読み直し + 検証 + 原子的置換) が終わる時間に比べて十分長く、
  かつ「保持者が本当に死んでいる」ことを見分けるのに十分短い値として選んだ。短すぎると
  正常に動いている書き込みを誤って stale 判定してしまい、長すぎると死んだセッションの lock を
  長時間引きずる。
- **`mv` で一時名に退避してから消す理由 (直接消さない理由)**: stale 判定は「複数のセッションが
  同時に」行いうる。もし直接 `rmdir` すると、2 つのセッションが同時に「stale だ」と判定して
  同時に削除を試み、片方が削除に成功した直後にもう片方が (既に無くなった) 同じディレクトリを
  消そうとしてエラーになったり、最悪、削除の直後に別セッションが新しく作った lock を巻き添えで
  消してしまう競合が起きる。`mv` (rename) はディレクトリ作成と同じくアトミックな操作で、
  **退避 (rename) に成功した 1 セッションだけが除去者になる** — 他のセッションは rename が
  失敗するので「自分は除去者ではない」と分かり、通常の待ちに戻る。除去者だけが実際の削除
  (`rmdir` 相当) を行うので、複数セッションが同時に stale 判定しても排他が破れない。

## 2. 原子的書き込み

一時ファイルに全文を書いてから `rename` で `state.json` に置き換える (移行前 108-116 行の
手順 3)。

- **なぜ一時ファイル + rename か**: `state.json` を直接開いて上書きすると、書き込みの途中で
  プロセスが kill されたり電源が落ちたりした場合に、ファイルが「前半は新しい内容、後半は古い
  内容」のような壊れた状態で残りうる。POSIX の `rename` は同一ファイルシステム内であれば
  アトミックなので、一時ファイルへの書き込みが完了してから rename すれば、読む側は常に
  「完全に古い内容」か「完全に新しい内容」のどちらかしか observe しない。
- **lock を取ってから state.json を読み直す理由 (書く前に読み直す理由)**: イテレーション冒頭に
  読んだ内容を、時間が経ってからそのまま書き戻すと、**間に入った他セッションの書き込みを
  巻き戻してしまう**。lock を取った直後にもう一度読み直し、自分の変更をその最新内容に適用する
  ことで、この種の失われた更新 (lost update) を防ぐ。読み直した内容が自分の判断の前提を覆して
  いる場合 (例: これから着手しようとしたタスクが既に別セッションで in_progress になっている)
  は、書かずにその処理自体を破棄する — これは `state.ts` の各書き込み verb が「前提チェック→
  書き込み」をロック区間内で一体として行うことで実現されている (`conflict` 終了コード)。

## 3. heartbeat と 2 つの閾値 (90 分 / 1440 分)

`state.ts session-touch` が自分の heartbeat ファイルを作成・更新し、同時に古い残骸を掃除する。
`state.ts sessions-alive` が生存セッション一覧を返す (移行前 123-131 行)。

- **なぜ 2 つの独立した数値か**: 「生きているとみなす年齢」(90 分) と「掃除する年齢」
  (1440 分 = 24 時間) は別の目的を持つ。90 分は**二重起動を防ぐための閾値** — 実行エージェントや
  watch プロセスが作業の区切りごとに heartbeat ファイルを touch するので、正常に動作している
  限りこの年齢に収まる。1440 分は**ディスク上の残骸を溜めないための閾値** — セッションが
  クラッシュして二度と heartbeat を打たなくなった後も、90 分の「生存」判定からはすぐ外れるが、
  ファイル自体は掃除されるまで残り続ける。1 日分は保持することで、90 分の失効判定に使う直近の
  履歴を誤って早期に消してしまう事故を避けている。
- **90 分の根拠**: 実行エージェントの 1 フェーズ (research/plan/implement/report のいずれか) に
  検証ゲートも含めて要する時間の実測上限に、余裕を見て設定した値。これより短いと、正常に長く
  かかっているフェーズを死んだと誤判定して不要な Status check や引き継ぎが発火する。
- **`session` を書き換える契機を 4 つに限る理由** (移行前「セッションの所有権」節): `session`
  フィールドの意味は「このタスクについて、そのセッションにしか無い揮発資源 (実行エージェント /
  watch プロセス) が今ある」ことの表明である。契機を絞らないと、**揮発資源が実際には無い
  状態で `session` だけが残る**組み合わせが生まれ、他セッションから「まだ誰かが作業中」と
  誤認されて引き取りが起きなくなる。4 契機 (起動/引き継ぎ・watch 起動・揮発資源消滅・ループ
  停止) は、いずれも「揮発資源の実際の生成/消滅」と 1 対 1 に対応するよう設計されている。

## 4. `executor_last_event_at` を 3 箇所でしか動かさない理由

移行前 101 行、375 行。更新するのは、その executor を起動したとき・その executor へ
SendMessage が**成功**したとき・その executor の停止通知を処理したときの 3 つだけである。

**失敗した送信で動かすと、他セッションから executor が生きているように見えてしまう。**
`executor_last_event_at` は「実行エージェントの生存判定」に使われる唯一のフィールドであり
(トップレベルの `updated_at` は無関係なタスクの追従処理でも動くため使えない)、この値が新しい
限り「稼働中なので何もしない」と判定される。もし SendMessage が失敗した (＝相手のセッションが
死んでいて届かなかった可能性が高い) にもかかわらずこの値を更新してしまうと、実際には死んで
いる executor がいつまでも「生きている」と誤判定され続け、誰も引き取れなくなる。3 箇所に
限ることで、この値が動くのは「実際に executor と何らかの意思疎通ができた」ときだけになる。

## 5. `in-review` の `tip` — コミット 0 件で入れてはならない理由

移行前 315 行。`finish=none` (コミット 0 件) のときに `review.tip` へ base と同じコミットの
sha を入れてしまうと、**`merge-base --is-ancestor <tip> <base>` が無条件に真になる** —
base 自身は常に base 自身の祖先だからである。これは「マージ済み」の判定条件そのものなので、
tip を base と誤って一致させると、まだ何もマージされていないのに「マージ済み」と誤判定され、
**マージの回収がそのタスクを done にしてしまい、未コミットの作業ごと worktree が削除される**
(「マージの回収」節: done にしたタスクの worktree は削除して問題無いという前提で動くため)。
`state.ts in-review` は `--commits 0` のときに `--tip` を渡すこと自体を `usage` エラーにして
おり (`state-cli-contract.md`)、この誤りを CLI 側で構造的に防いでいる。

## 6. `stalled_since` を空振りで進めない理由

移行前 99 行、631-634 行 (「停滞」節)。

- **回数ではなく時刻で持つ理由**: (a) 複数 PR の追従を同時に持っているとき、空振りの回数を
  数えると「PR ごとの空振り」と「打ち切りまでの回数」の対応が崩れる — 例えば 2 本の PR が
  交互に 2 回ずつ空振りしても、それぞれの PR は「まだ 2 回」なのに合算すると「4 回」になり、
  「4 回で 1 日」という等式が成立しなくなる (PR ごとにカウンタを分ける複雑さが要る)。時刻は
  監視している PR の本数に依らず「最後に何か起きてからどれだけ経ったか」を直接表せる。
  (b) 固定間隔 cron 配下では、watch プロセスの `timeout` 通知が構造的に届かない (プロセスが
  イテレーションを跨げないため)。この運転形態では「何もしなかった空振り」という事象自体を
  数える手段が無いが、catch-up 観測が「起きたか」を毎回判定するので、時刻ベースならこの劣化
  モードでも同じ規則が使い続けられる。
- **進む条件**: watch プロセスが `changed` で終わった / 観測サブエージェントが `fix`/`merged`/
  `closed` を返した / 観測で `watch.head` か `watch.ci` が前回の値から変わった、のいずれか。
- **進まない条件**: `timeout` 終了 (6 時間何も動かなかっただけ)、`wait`/`clean` のまま `head`/
  `ci` が変わらない観測 (CI 実行中または既に緑で指摘も無い、という「変化していない」状態)、
  観測が `error` (観測できていないだけで、動いた証拠にはならない — 誤って進めると、実際には
  レビューが止まっている PR の打ち切りが遅延し続ける)。

## 7. その他の根拠

- **`relisted` の 10 分ルール** (移行前 106 行、183-189 行): 複数セッションが同時に `list` を
  呼ぶと、数秒差で 2 つの `list` 結果に同じタスクが「まだ載っている」形で現れることがある
  (トラッカー側の反映遅延)。これを「ユーザーが復帰させた」と早合点すると、in_review のタスクが
  既存 PR の上でまるごと再実行されてしまう。初回観測から 10 分以上あけた 2 回目の再登場だけを
  復帰とみなすのは、通常の反映遅延は次の refresh (数十秒〜数分) で解消するため、10 分後にまだ
  載っているなら反映遅延ではなくユーザーの明示的な操作である、という経験則による。承認手順の
  ループ間隔をこの判定のためだけに 30 分空けるのも同じ理由 — 判定の根拠 (10 分残っていること)
  を、次の `list` が確実に観測できるようにするため。
- **`withdrawn_branches` が `base` だけを運ぶ理由** (移行前 105 行): 取り下げで queue から
  外したタスクのエントリを丸ごと消すと、`base` (分岐元のブランチ) の記録が失われる。後日
  ユーザーがトラッカー側でそのタスクを復帰させると、worktree/ブランチの再利用経路
  (`state.ts set-worktree`) が新しい base を推測することになるが、推測が分岐元とずれると、
  マージ回収の判定 (`merge-base --is-ancestor`) が前回のコミットを今回の成果として誤って
  数えてしまう。`base` だけを最小限に運ぶことで、この誤判定を避けつつ、他の情報 (PR の内容や
  レビュー履歴) は queue のエントリと一緒に破棄してよいことにしている。
- **`watch.sig` を張り直しごとに null に戻す理由 (catch-up 観測の起点)**: `watch.sig` は
  「最後に観測が完了した時点の PR の署名」を表す。push 直後 (レビュー待ちに入った直後・
  `pr_fix` の push 直後・載せ直しの force push 後) は head が変わっているので、古い署名を
  そのまま watch プロセスに渡すと、**自分自身の push を「変化」として検知してしまう**
  (無意味な自己反応)。かといって新しい署名をその場で取り直すと、**それまでに届いていた
  レビュー指摘がその署名に焼き込まれ、以後どれだけ待っても `changed` にならない** — CI の
  無いリポジトリでは、その指摘は永久に観測されないまま埋もれる。この矛盾を解くのが catch-up
  観測で、張る前に 1 回だけ通常より深く観測することで、焼き込まれる前の変化を回収してから
  基準署名を取り直す。
- **`fix_attempts`/追従の 3 往復上限**: 押し直しがそのまま新しい CI とレビューを呼ぶため、
  上限が無いと理論上無限に往復しうる。3 回で打ち切り、以降は人のレビューに委ねることで、
  自動修正が机上の空論的なコメントの往復に陥るのを防ぐ。ユーザーが `watch.state` を
  `watching` に戻せば手動で再開できる。
